    fd12_training: Predictor Training and the FTB Update Bubble¶

    Open waveform

    Runs Surfer in the browser, with nothing to install. The signal setup takes a few seconds to apply.

    fd12_training is the FD-12 demonstration scenario. It is a demo, not a verification test. It runs nested counted loops whose body holds every kind of control transfer the predictors train on: conditionals, an indirect jump, an indirect call and its return. Each retired control transfer is resolved by the backend, converted by ftq_upd_conv into per-predictor updates, and presented to the cluster; each FTB update withholds one p0 request. The run passes if every predictor receives at least one update and at least one p0 request is withheld for an FTB update.

    The scenario runs on the one-slot model (Makefile SCEN_2S, DOC-006). A recorded run:

    -I: fd12_training: PASS, update cycles uBTB 154, loop predictor 111, FTB 154,
    TAGE 111, SC 111, ITTAGE 28, RAS commit 28, p0 holds for an FTB update 154,
    cyc 454

    1. The program¶

    Source: programs/fd12_training.svh, task prog_fd12. Bare M-mode, code at RESET_VECTOR 0x8000_0000 (bp_defines_pkg.sv:40). Addresses below are derived from the writer's emitters (mixed is c.addi, addi, c.addi repeating: 2, 4, 2 bytes).

    0x8000_0000  mixed(4)                                     10 bytes
otop = +0x0A mixed(2)                     outer body
itop = +0x10 mixed(3)                     inner body
       +0x18 bne x6,x0,itop               inner loop branch, 6 passes
       +0x1C beq x0,x0,+0x28              always taken
       +0x28 mixed(2)
       +0x2E jalr x0,0(x7)  -> +0x6E      indirect jump
       +0x6E mixed(2)
       +0x74 jalr x1,0(x28) -> fn         indirect call
       +0x78 mixed(1)                     return lands here
       +0x7A bne x6,x0,otop               outer loop branch, 14 passes
       +0x7E mixed(3), jal x0,0           halt
fn = 0x8000_0800  mixed(3); jalr x0,0(ra) -> +0x78   return
    • The loops are built by loop_br and rep_iter (rtl/core/frontend/fe_top/tb/models/fe_tb_writer.svh:352, :364): the body is written once and its expected-stream entries are replicated, the last execution of each loop branch not taken.
    • rep_iter(eo, 14) replicates the outer body including the six inner passes already expanded, so the stream holds 14 x 6 inner branches.
    • jalr_to (fe_tb_writer.svh:389) types the jump by the RAS hint rules: jalr x0,0(x7) is INDIRECT_NONRET, jalr x1,0(x28) is INDIRECT_CALL; ret (:280) is RETURN.

    Control transfers in the stream, per outer pass: 6 inner branches, the always-taken beq, the indirect jump, the indirect call, the return, the outer branch. Over 14 passes: 154 transfers, of which 112 conditionals (8 per pass), 28 indirect (jump and call) and 28 RAS operations (call and return). The halt (jal x0,0) is the stream's last entry; the counts below (154, not 155, for the uBTB and FTB) show that its update falls after the measurement window closes.

    2. Why the program produces the behavior¶

    1. Resolution and conversion. ftq_upd_conv (rtl/core/frontend/ftq/rtl/ftq_upd_conv.sv) forms the per-slot uBTB, LP, TAGE, ITTAGE and SC payloads from the resolved record. A slot's predictor valids are presented only when the slot is accepted by every predictor it trains (upd_acc, lines 136-138 and 171; the handshake is described in the file header, lines 29-37).
    2. The cluster's type gate. bp_cluster classifies each update channel from its uBTB payload (upd_br_type, rtl/core/frontend/bpu/rtl/bp_cluster.sv:1739-1746) and fans it out by type (fe_decisions.md 7.2):
    3. uBTB: any type but NO_BRANCH (bp_cluster.sv:1752-1753)
    4. LP: conditionals (:1678-1679)
    5. TAGE, SC: conditionals, each also gated by its queue ready, SC by sc_enable (:1798-1807)
    6. ITTAGE: INDIRECT_NONRET and INDIRECT_CALL (:1744-1746, :1801-1803)
    7. FTB: its own channel, for a branch or a jump (:1643-1644)
    8. RAS commit: DIRECT_CALL, INDIRECT_CALL, RETURN, RETURN_CALL (:1649-1653)
    9. The FTB update bubble. The FTB has one read port. When ftq_ftb_sched will issue an FTB update next cycle (issue_next, rtl/core/frontend/ftq/rtl/ftq_ftb_sched.sv:327, wired to h3_ftb_upd at ftq.sv:493), ftq_npc holds its p0 request (hold term H3 in w_hold, ftq_npc.sv:307-309; rationale at ftq_npc.sv:132-137). One p0 request is withheld per FTB update.

    3. What the monitor counts¶

    The counts come from tb/fe_demo_mon.svh:502-514, sampled every cycle while the stream is being measured (meas, rtl/core/frontend/fe_top/tb/models/fe_tb_backend.svh:416). They read the valids after the cluster's gates.

    n_upd_ubtb   per slot: w_ubtb_upd_u0[s].valid, summed over the slots
             of the cycle (DOC-002)
n_upd_lp     cycles with w_lp_upd_val_p0 != 0
n_upd_tage   cycles with w_tage_upd_val_u0 != 0
n_upd_itt    cycles with w_ittage_upd_val_u0 != 0
n_upd_sc     cycles with w_sc_upd_val_u0 != 0
n_upd_ftb    cycles with w_ftb_upd_val_u0
n_upd_ras    cycles with w_ras_commit_val
n_ftb_bub    cycles with u_ftq.u_npc.h3_ftb_upd

    The proof (tb/fe_demo_proofs.svh:108-110) requires every one of the eight counts to be non-zero. tb_fe_demo.sv also requires the whole stream to retire with no errors before it accepts the proof.

    4. Reading the numbers¶

    • The figures match the program's control transfers but for one: uBTB and FTB 154 (every transfer), LP, TAGE and SC 111 (the conditionals, less one), ITTAGE 28 (the indirect jump and call), RAS commit 28 (the call and the return). FTB update p0 holds 154: one per FTB update.
    • The conditional left out is the always-taken beq at +0x1C, resolved at cyc 168 in a block from +0x10 whose one slot holds the inner loop branch at position 4. The FTQ places its resolution in that occupied slot, whose prediction metadata describes the other branch, so the uBTB and FTB updates form and the LP, TAGE and SC updates are suppressed (item C, BP-139, rtl/core/frontend/ftq/rtl/ftq_resolve.sv lines 46 to 57). The condition is rsv_plc_occ (line 443), which gates the updates at lines 551 to 560. It is the only such resolution in the run.
    • Except n_upd_ubtb, the counters count cycles with any slot valid, not slot updates; the result line says "update cycles" for that reason. DOC-002 changed n_upd_ubtb to sum its slots. On this model a cycle has one slot, so every count is of single-slot updates.
    • The run takes 454 cycles on this model and 459 on the two-slot model (DOC-007 run). On the two-slot model the LP, TAGE and SC counts are 112, since the beq has a slot of its own.
    • Departure from planning/showcase/fe_demo_scenarios.md FD-12: the program there is "any branch, first execution and the next"; the program as built is tb_fe_top's loops, with every update type, so that the proof can require an update at each predictor. The proof as built adds the RAS commit to the predictors FD-12 names.

    5. Waveform¶

    The saved view is waves/fd12_training.sucl, which make view S=fd12_training opens in Surfer. Groups: clock, backend, ftq_upd_conv, ftb_update, bp_cluster_p0. Look at:

    • bkend_ftq_rsv_val: a resolution from the backend.
    • w_ubtb_upd_u0.[0].valid, w_lp_upd_val_p0, w_tage_upd_val_u0, w_sc_upd_val_u0, w_ittage_upd_val_u0, w_ras_commit_val: the updates after the cluster's gates, by type.
    • ftb_upd_valid_u0 with ftb_upd_pc_u0: an FTB update; in the cycle before it u_npc.h3_ftb_upd is high, u_npc.w_hold is high and ftq_pred_val_p0 is low: the withheld p0 request.
