## Reset state

On reset 

- `pc` <= reset vector, Pacino uses `0x00_80000_0000`
- FTQ valid bits are cleared
- FTB valid bits are cleared
- All predictors are in their reset initialization state

On the rising edge of reset the BPC elements begin their SRAM initialization
sequence which initializes the predictor state. Once a cluster element 
finishes it's initialization the element asserts ready, e.g. `tage_rdy`.

Reset state for the BPU is active until the all elements in the BPC have
returned their ready signals. `bpu_cntrl` gathers the cluster element readys
to form a `bpu_rdy` signal. 

No front-end behavior occurs before `bpu_rdy` is asserted. Once `bpu_rdy`
is asserted the reset state is exited.

## Staged prediction response (s1/s2/s3): the override model

Answers the FIXME in the prediction-response pseudocode above: does the
BPU wait for s1/s2/s3 to all complete before responding, or stream each
stage as it completes ?

The BPU does not wait. The response channel is a single Decoupled
valid/ready port that can go valid every cycle. s1, s2, s3 are the three
pipeline taps of the predictor, each holding a different in-flight fetch
block:

- s1 holds block A     (1-cycle predictors: uBTB, loop predictor)
- s2 holds block A-1   (2-cycle predictors: FTB, TAGE)
- s3 holds block A-2   (3-cycle predictors: SC)

s2_pc is s1_pc registered one cycle; s3_pc is s2_pc registered one cycle
(BPU.scala:296-297). The three fields are three blocks at three ages,
not three views of one block.

### When resp.valid asserts

resp.valid asserts in three independent cases (BPU.scala:444-447):

```
  resp.valid =
      s1_valid && s2_components_ready && s2_ready   // s1 enqueue
   || s2_fire  && s2_redirect                       // s2 override
   || s3_fire  && s3_redirect                       // s3 override
```

- s1 enqueue: the fast-path prediction is sent as soon as the 1-cycle
  predictors produce it. Common case, one per cycle.
- s2 override: sent only when s2 (FTB/TAGE) disagrees with what s1 sent
  for that block (s2_redirect -> hasRedirect).
- s3 override: sent only when s3 (SC) disagrees with what s2 sent.

If a later stage agrees with the earlier stage it does not re-assert
resp.valid for that block. There is no wait-for-s3. A correct fast-path
prediction is enqueued at s1 and never re-sent. s2/s3 consume channel
bandwidth only when they correct a younger prediction. This is why the
staged structure is not a performance problem: it is an override
pipeline, not a barrier.

### How the FTQ consumes it

The FTQ picks the most-advanced stage that redirects, priority
s3 > s2 > s1 (FrontendBundle.scala:717-731):

```
  selectedRespIdxForFtq = PriorityMux(
    s3.valid && s3.hasRedirect -> BP_S3,
    s2.valid && s2.hasRedirect -> BP_S2,
    s1.valid                   -> BP_S1)
```

- On s1 (enqueue): allocate a new FTQ entry at bpuPtr, write it, and
  increment bpuPtr (NewFtq.scala:569, 574, 695).
- On s2/s3 override: rewrite the already-allocated entry in place at the
  stage own ftq_idx (NewFtq.scala:570, 574). The BPU flushes the younger
  in-flight stages (s1_flush/s2_flush, BPU.scala:383-387) and resteers
  its own s0_pc from s2_target / s3_target.

### Why the resp carries all three at once

All three blocks are live in the same cycle and the FTQ acts on all
three that cycle:

- s1 payload to enqueue a fresh block,
- s2/s3 payload + hasRedirect + ftq_idx to override the correct
  already-enqueued entries,
- s3 (lastStage) to write the final training metadata.

The training payload is a single s3 copy, not one per stage:
last_stage_meta, last_stage_ftb_entry, last_stage_spec_info are written
whenever s3 is valid (NewFtq.scala:588-604). This is why the response
has three prediction structs but only one meta / ftb_entry set.

### The FTQ index does not come from the FTB entry

The FTB entry stores branch offsets, target low-bits, and fall-through.
It does not store an FTQ index. The index on each stage is:

- s1: bpuPtr, the FTQ enqueue pointer. s1.ftq_idx is DontCare in the BPU
  and the FTQ substitutes bpuPtr (NewFtq.scala:574).
- s2/s3: the pipelined pointer for that in-flight block, s2_ftq_idx /
  s3_ftq_idx (BPU.scala:759, 764).

### Pacino mapping

The Pacino latency ladder maps one-to-one onto the XS stages:

```
  s1 (1 cyc)  uBTB, loop predictor   enqueue, the fast guess
  s2 (2 cyc)  FTB, TAGE              override s1 on disagree
  s3 (3 cyc)  TAGE+SC                override s2 on disagree
```

Keep the same override contract: enqueue on s1, and let s2/s3 re-fire
the response only to correct a younger prediction. Do not build one
response that waits for all three stages of a single block. That
serializes prediction behind the slowest predictor and removes the
run-ahead the decoupled front end exists to provide.

## IFU FTQ/FTB

IFU has been directed to fetch a block of instructions. When this block is 
returned it is pre-decoded to if there are branches in the fetch block
and how many. 


Predecode information is supplied to the FTQ. This information is inspected
and if necessary a structure is sent to the FTB to allow it to create and
an FTB entry.
