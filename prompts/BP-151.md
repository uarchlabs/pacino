## What the results establish

**fb_stale_top is TD#207.** In this design, committing a call moves BOS
up to TOSR, so after an immediate commit the speculative stack is
nearly always empty. Most returns then fall back to the commit stack.
The commit stack does not see speculative pops, so its top can be a
frame an uncommitted return has already popped.

The timing curves follow from this:

- With fast commit (media_2 at (0, 0)), nearly every return depends on
  the fallback, which gives 4,739 mispredicts.
- With slow commit, the frames are still speculative: 8 at (5, 5).
- The rise with C on infra_1, compress_1 and int_6 is the same window
  seen from the other side.

The specification's gap is a sentence in ras_decisions.md 4.4: the
fallback "falls through to the commit stack ..., which is architectural
state". It is architectural only for frames no speculative return has
consumed. Every rule is met, and the rules are what is wrong.

**The size of the prize:**

- A1 plus B1 (cskip) predicts the right target for every fb_stale_top
  and stale_below_bos return the IA measured.
- At immediate that removes 4,742 of media_2's 4,815 return
  mispredicts, and 11,215 of infra_1's 14,707, about 5.6 MPKI on
  infra_1.
- This is the largest single MPKI change found in the front end so far.

**The other causes:**

- **call_pd (H4)** is real and is web_11's main remaining cause: 2,585
  to 3,383, about 1.3 to 1.7 MPKI.
- **TD#149 (snap_repair):** 7 returns. TD#149's "fix if measured worse"
  is not met.
- **Smaller causes:** the wrap (H1, at most 1 per run), H2 (never the
  first cause), true depth (0), p3_reach (up to 54), snap_offpath_op

**commit_unexecuted is a real FTQ defect** against ftq_decisions.md 5.4.
There are two mechanisms:

- **(b), two resolutions of one entry in one cycle:** a plain defect.
  The IA located it and named the fix: make the end clear positional,
  or make the younger resolution's view match the writes actually made.
  It wasn't built only because fe_tb_backend.svh was outside AUTHORITY.

## Hypothesis
Return mispredicts on slot-held returns come from one or more RAS
causes that the backend's timing changes the rate of. Candidates, from
the documents (the IA confirms or rules out each, and finds any
other):
- H1 THE SPECULATIVE STACK WRAPS. It has 16 entries
  (RAS_SPEC_ENTRIES) and frees an entry only as BOS advances on
  commit. When commit lags, more pushes are in flight than it holds,
  and a restore across the wrap is not exact (12.9 RE7). This would
  rise with resolve to commit.
- H2 THE RESTORE'S BOS. A restore loads BOS from the named entry's p2
  snapshot (4.3, RE1), which may predate commits that have moved BOS
  since; a restore and a commit in one cycle take the restore's BOS
  (CO11). This would depend on the order of resolve, redirect and
  commit within a few cycles.
- H3 THE p3 REPAIR IS NOT IN THE SNAPSHOT (TD#149, RP10). A restore to
  an entry repaired at p3 undoes the repair.
- H4 A CALL ONLY PREDECODE FINDS. The speculative push is made at p2
  from the FTB's type only (section 7, 12.4); a call the FTB missed
  and predecode found is never pushed, and its commit pushes the
  entry's pft_addr, which a predecode correction does not rewrite
  (ftq_entry.sv ras_commit_payload, its header comment), not the
  call's pc + 4.
- H5 TRUE DEPTH. The program's live call depth exceeds what the
  speculative and commit stacks hold (16 + 32), or deep recursion
  exceeds the recursion count.
