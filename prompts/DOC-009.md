## Assumptions made not explicit in the prompt
1. "A cycle the description presents as exact" (FDT-10c): only cyc 0,
   the release of reset, which is exact by definition. Every other
   event is checked by window, since the descriptions give cycles from
   a run. A count or value an event states (uaon reaches 8, PPN
   0x81000, cause 20, position 9, r_count 52, a target address) is
   part of its condition, so it must match exactly for the event to
   be seen at all.
2. An event's cycle is the first cycle its condition holds; the
   condition is written specifically enough to name the event (for
   example "first taken B resolved" is the backend redirect to B's
   target). An event the table states as the last of its kind takes
   the last cycle its condition holds ("last" in the listing).
3. The window is max(8, cyc / 10), integer division, centred on the
   row's cyc (FDT-10c "a tenth of its value, and at least 8 cycles").
4. "The run ends" is cyc_run, the cycle count the result line
   reports. It is given directly by the testbench (evt_at), not by a
   signal condition, and it is counted as checked.
5. A failed event check fails the scenario like a failed proof, and
   prints one -E: line per failed check before the result line
   (FDT-10a format).
6. Problem 3 "each scenario's checks are shown to fire" was read as all
   24 scenarios, and was shown for all 24.

## Decisions made not explicit in the prompt
1. THE CYCLE OF AN EVENT (PROVISIONAL, no planning text sets it). It is
   the cyc at the first instant the waveform shows its condition, which
   is where the marker of its row sits (FDT-12c). Conditions are
   sampled at each rising edge before it updates anything. A design
   register changes at the edge, so it is recorded at that cyc. A
   signal the testbench drives (the backend's redirect, resolution and
   commit watermark, at the edge plus 1 time unit), or design logic
   combinational from it (the TAGE update and allocation, the update
   valids), shows the previous cycle's value at the marker instant.
   Such a check is "late" and records cyc + 1. Found on fd09: the
   backend redirect is high from t=746 to 756 (cyc 71 begins at 745,
   cyc 72 at 755), and the table says 72. With the rule, all 46 rows of
   the four existing tables match exactly. Each late flag was checked
   against the FST, where testbench-timed signals change at times
   ending in 6 and design registers at times ending in 5. One flag
   first set wrongly (fd07 RAS commit, which rises at the edge) was
   corrected this way.
2. Rows are matched to checks by the FDT-12c marker label (the event
   text up to ';', ':', ',' or '(', six words), not by position. A row
   with no check, a check with no row, or a duplicate label fails the
   run, and mk_sucl.py --svh rejects a label used twice in one table.
   So a changed row text, a swapped order or a table edit cannot pass
   unseen. The cost: a description author who rewords the start of an
   event must update the check's label.
3. The expected values reach the testbench as a file generated at
   build time from the descriptions (mk_sucl.py --svh), written into
   each model's directory. It is not committed, and there is no JSON
   or hand-copied list (Binding Previous Decisions). The parser is
   mk_sucl.py's own, so the markers and the checks read one table the
   same way.
4. Event wording in the 20 new tables avoids '-' and '.' inside the
   first six words (cbo.inval, FENCE.I, guest-page), because the label
   function strips them, as with "FENCEI".
5. tools/regress_demo.sh takes an optional ROOT argument, as
   regress.sh does, for the scratch demonstrations. With no argument
   it is the repository root.
6. The Makefile gained scenario_list so the script keeps no second
   copy of SCENARIOS or SCEN_2S.
7. fd17: an exit event for the loop was dropped; the last back edge is
   predicted correctly, so there is no misprediction to show.
