## The rename, and why RC_UNSPEC

Requirement 4 asked for existing conventions. XiangShan has none to
lift: it carries no redirect-cause enum at all. Its RedirectLevel is
flush / flushAfter with flushItself(level), which is Pacino's
bkend_ftq_redir_self, already present. The cause enum is a Pacino
addition with no counterpart.

So the name comes from Pacino's own conventions. The existing
members are RC_ plus one word naming the cause: RC_MISPREDICT,
RC_TRAP, RC_REPLAY.

```
  RC_UNSPEC    CHOSEN. Names the defining property -- the cause is
               not attributable to any instruction the FTQ tracks.
               Matches the reviewer's own framing, unspecified
               instruction.
  RC_UNCOND    REJECTED. XiangShan has a commented-out
               isUnconditional for this concept, so there is
               precedent, but bp_br_type_e already uses UNC for
               unconditional branches in DIRECT_UNC. Two meanings
               of one abbreviation in one package.
  RC_SYNC      REJECTED. RISC-V calls fence.i and sfence.vma
               synchronization, but those ARE instructions and name
               an entry. Naming this cause SYNC would invite them
               to be encoded here, which 5.1 explicitly forbids.
  RC_FLUSH     REJECTED. Reusing the one word this project has
               circled for months, immediately after deciding it
               names nothing distinct.
  RC_EXTERNAL  REJECTED. True of reset and debug entry, but it
               names the source rather than the property, and would
               misname any future internal cause with no
               instruction.
```
