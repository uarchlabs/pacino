# Task Overview

Widen FTB_BR_POS_BITS from 3 to 4. In-block positions become 2-byte
granular, sixteen per 32-byte block, so a branch beginning at any
RVA23 C-extension boundary has its own position. Closes the aliasing
of two RVC branches in one aligned word.

Prerequisite BP-098, which separated the position granularity shift
from the predictor index-hash shift.

## Context Comments
FTB_BR_POS_BITS = $clog2(FTB_BLOCK_BYTES / 4) = 3 gives eight 4-byte
positions per 32-byte block. RVA23 mandates the C extension, so a
branch may begin at any 2-byte boundary and two RVC branches inside
one aligned word share a position.

The consequence was recorded in three places and accepted in two of
them: bp_history_interfaces.md lines 188-192 ("Two RVC branches
inside one four-byte slot therefore share a position and contribute
the same path bit"), ftb_decisions.md 4.4, and
ftq_ifu_interfaces.md 10, which stated the effect -- the entry can
describe only one of the two, so the FTB and uBTB train them as one
branch with interfering directions.

A fourth consequence surfaced while writing
ftq_backend_interfaces.md: the backend returns an in-block position
at resolution and the FTQ maps it to a prediction slot. With shared
positions that mapping is ambiguous, so a resolution can train the
wrong branch's metadata.

BP-098 removed the blocker. INST_OFFSET carried both the position
granularity and the predictor index-hash shift; it is now
POS_OFFSET_BITS, derived as FTB_OFFSET_BITS - FTB_BR_POS_BITS, and
PC_HASH_SHIFT. Widening the position therefore rescales the
fall-through path on its own and leaves every predictor hash alone.

## Hypothesis
The widening is a parameter change, not a redesign. Every affected
width in the RTL is a declaration of the form logic [X-1:0], so all
18 lint targets should pass with no RTL source edit beyond the two
parameter derivations. The fallout should be confined to testbench
literals and to the two places that encode the position-to-address
arithmetic: the branch PC in tb_bp_cluster group E, and the
bp_history path-bit identity BP-092a proved.

## Background
Costed before the decision at +9,472 bits, about 3 percent of the
FTB, uBTB and FTQ storage, plus roughly 190 hardcoded 3-bit position
literals and the path-bit identity moving from pos[1] ^ pos[0] to
pos[2] ^ pos[1]. Recorded in ftq_ifu_interfaces.md 10.

## Binding Previous Decisions
- BP-098: POS_OFFSET_BITS is derived and must stay derived.
  PC_HASH_SHIFT must NOT change; changing it rehashes every table.
- bp_cluster BR_POS_SHIFT is derived and is commented as
  intentionally rescaling with a position-width change.
- IC-FTB-16: the conditional fields are filled in program order.
- ftb_decisions.md 4.2: target displacement widths are set by ISA
  reach, NOT by in-block granularity. They do not change here.

## Specific Requirements

   and +1, and the UBTB_ pair likewise.
2. No RTL logic change. Any RTL edit beyond the parameters and
   stale width comments is a finding, not an expected outcome.
3. Locate the testbench position literals from the compiler's own

4. Rebase group E on derived expressions rather than substituting

5. PC_HASH_SHIFT unchanged.
6. All 47 targets green. Report every count that moves and why.

## RVA23 compliance risks and gaps noticed

- CLOSED by this task. A branch beginning at any 2-byte boundary now
  has its own position. Previously two RVC branches in one aligned
  word shared one, so the entry could describe only one of them, the
  FTB and uBTB trained them as a single branch with interfering
  directions, they contributed one path bit instead of two, and the

  the same TAGE, ITTAGE and SC index. Deliberately untouched here.
  Changing it rehashes every table and invalidates all tuning, and
