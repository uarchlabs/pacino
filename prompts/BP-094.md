# Task Overview

Fix the branch_id staging defect BP-093 found, and close the
two verification holes that let it survive this long.

tage_cntrl.sv assigns meta_p1[s].branch_id from
tage_pred_inp_p0[s].branch_id inside the p1 meta_p1
always_comb. branch_id is the only meta_p1 member not staged
p0 -> p1, so the branch_id arriving at p2 belongs to the
request presented one cycle LATER than the one the rest of the
metadata describes.

At the cluster boundary, where every p2 and p3 comparison is
qualified by branch_id equal to the FTQ index in the matching
stage register:

  - unstalled back-to-back stream: the guard never matches, so
    the TAGE direction and the SC correction never reach the
    FTQ at all;
  - stalled stream: the guard matches for the WRONG entry.
    BP-093 D2 observed 4 accepted responses out of 32, each
    carrying a different request's branch_id.

The second case is the serious one. The guard is defeated
precisely in the scenario it exists to catch.

SC inherits the same skew, because sc_pred_meta_p3.branch_id is
copied from the staged TAGE metadata. Confirm that rather than
assume it.

Two verification holes let this stand. tb_tage is green because
it does not vary branch_id across requests. tb_bp_cluster works
around the defect with req_a(), which repeats the FTQ index on
the following cycle, in every TAGE and SC case. Both are closed
here.

BP-093 test C0 PINS the defective value deliberately, so it
will fail when this fix lands. That is the design: it forces
this revisit. Rewrite it to the specified behaviour.

Groups G and H are in this task. Group G is the closed
predict-then-update loop across all seven predictors. Group H
is the SC credit arbiter, implemented in bp_cluster and never
tested. Together they close every line BP-093 left uncovered in
bp_cluster.sv.

BP-093's A3 X-check cannot fail under Verilator's two-state
model and is replaced with one that can. FE-11 is proven in the
stream this task builds. The BP-093 mutation set is re-run,
because the fix changes what is reachable.

## Hypothesis

branch_id can be staged p0 -> p1 alongside the rest of meta_p1
without changing any other TAGE behaviour, any port, or any
struct.

Once it is, the cluster's branch_id qualification works as
specified: a response is accepted when its branch_id equals the
FTQ index in the matching stage register and rejected when it
does not, in both the unstalled and the stalled stream.

SC needs no change of its own, because its metadata branch_id
is copied from the staged TAGE value.

## Background

BP-093 was the first simulation of bp_cluster. It found this
defect at test C0 and characterised it at test D2. The full
evidence is in prompts/BP-093.md: the Summary, test C0, test D2
and Deferred Work item 1.

The cluster is not at fault. It compares what it is given, and
BP-093 found no defect in bp_cluster.sv. The metadata reaching
it is wrong.

Every TAGE-dependent and SC-dependent case in tb_bp_cluster

following cycle so the skewed branch_id happens to match. That
was the minimum construction that let the cluster's own
TAGE-hit and SC-hit arms be exercised at all while the defect
stood. It is a workaround and it narrows what those tests
prove.

### R6. tb_tage -- new directed test, proved against the unfixed RTL

`pred_branch_id_stage_tst` added, enabled by `_pred_branch_id_stage_tst`
and dispatched at the end of test_body.

Why the hole existed: every other prediction test in tb_tage drives
one request at a time with branch_id at a single value, so a live p0
read and a staged one are indistinguishable. The new test VARIES
branch_id across CONSECUTIVE requests, on both slots, from disjoint
ranges, and additionally couples the check -- the two PCs are seeded
with DIFFERENT T0 counters, so each response carries a CTR and a
direction that identify which request produced it. The assertion is
not "branch_id looks plausible" but "branch_id and the rest of the
struct name the SAME request".

Mechanisms seeded or read out of the DUT rather than assumed:
aging off; uaon cleared on both slots; T1-T4 invalidated in every row
of both banks of both slot RAMs so T0 is the sole provider and no
earlier test's residue can alias; the two T0 rows located by READING
t_idx_r1[0][0] out of the DUT, never by replicating the index hash.

(0x30000 / 0x34000) turned out to share T0 index 0 -- they differ only
ABOVE the index field. The test's own collision check caught it and
failed rather than silently comparing one seeded row against itself.
The pair was changed to 0x30040 / 0x30800 (indices 16 and 512, and in
different banks).
