## Background

The FTQ decouples prediction from fetch. Three pointers over a 64
entry array: alloc_ptr allocates at p0 when a prediction request is
accepted, fetch_ptr issues fetch requests, commit_ptr frees entries
as the backend retires them. The gap between fetch_ptr and alloc_ptr
is the run-ahead the FTQ exists to provide.

Pointers are seven bits: FTQ_IDX_BITS low bits index the array, the
top bit is the wrap generation. Empty is all three equal; full is
alloc_ptr[5:0] == commit_ptr[5:0] with alloc_ptr[6] != commit_ptr[6].

The commit input is a watermark, not a pulse, and may jump several
entries at once. The walk toward it is rate limited to one entry per
cycle by the scalar RAS commit port on bp_cluster.

## Binding Previous Decisions

1. THREE POINTERS. ftq_decisions.md 5.4: commit and free are the
   same pointer. The commit payload reads bp_ras_snapshot_t out of
   the entry, so an entry cannot be freed before its RAS commit is
   issued. Do not add a separate deallocation pointer.

2. ALLOCATION IS AT p0, NOT p1. ftq_decisions.md 5.2. ftq_pred_idx_p0
   leaves with the request, so alloc_ptr advances when the request is
   accepted. The entry CONTENT is written at p1 by a different
   module. fe_decisions.md 2.3 says the FTQ allocates at p1; that
   describes the entry write, not the index.

3. ALLOCATION IS UNCONDITIONAL. An entry is allocated for every
   prediction block including one the p1 predictors miss.

4. COMMIT_PTR NEVER REWINDS. ftq_decisions.md 5.5 R2. Committed is
   architectural. A redirect can only name an index at or after
   commit_ptr; that is the backend's obligation and this RTL does not
   arbitrate it.

5. RAS SUPPRESSION. ras_decisions.md 4.5 rules restore > commit >
   hold for BOS. In a cycle where a redirect restore fires, the FTQ
   suppresses the RAS commit it would have issued and the walk does
   not advance that cycle.

6. RC_UNSPEC IS UNCONDITIONAL. ftq_backend_interfaces.md 5.1: _idx,
   _pos and _self are meaningless and must not be read. Every entry
   is squashed, not entries after an index.

7. FULL IS THE ONLY STALL. ftq_decisions.md 5.1: full is hold
   condition H2 of section 4.5 and is the only condition under which
   the FTQ stops predicting.

## Test Matrix (testbench sessions only, omit otherwise)

TWO TESTBENCHES, tb_ftq_ptr and tb_ftq_commit, not one covering
both. Each instantiates its own DUT and MODELS the other module's
pointer as a driven input. The reason is stimulus control: the
required cases need the queue placed at exact occupancies -- one
short of full, exactly full, straddling the wrap, commit_ptr held
while allocation laps the array -- and a wired pair makes each of
those a function of the other module's advance rules rather than
something the case can set. The cross-module behaviour is covered
instead by the bound properties, which hold against any legal input
sequence rather than the one sequence a wired pair happens to
produce. Every driven sequence is legal: tb_ftq_ptr never drives
commit_ptr past fetch_ptr, tb_ftq_commit never drives alloc_ptr
behind commit_ptr or beyond the allocation limit.

Common to every case below:
- Setup: rstn low for 4 cycles, all inputs cleared, then rstn high
  for 2. No case carries state from the previous case; each group
  calls do_reset() and walks to its start state through the driven
  interface.
- Pass criterion: the named signal matches the expected value at
  the observation point, plus zero firings from the bound
  properties for the whole run.
- There are no RAM or table structures in either module. Both hold
  flops only -- two pointers in ftq_ptr, one pointer and one walk
  end in ftq_commit -- so there is no residue to invalidate and no
  hash or tag value to derive. This is stated because the
  self-contained-test rule requires the enumeration, not because
  the enumeration is long.

## Assumptions made not explicit in the prompt

A1 ACCEPTANCE OF A PREDICTION REQUEST is modelled as
   alloc_req_val & alloc_req_rdy. 5.2 says alloc_ptr advances
   "when the request is accepted" without naming the handshake.
   alloc_req_rdy is hold condition H1 of 4.5 -- every queued
   predictor able to take the request -- and H2 is formed inside
   this module as ftq_full. The two are kept apart on the port
   list because they come from different places.

A2 FETCH ISSUE is ftq_ifu_req_val & _rdy, which 5.1 states
   directly.

A3 THE REDIRECT INPUT is the already-arbitrated winner published
   by ftq_npc per 7.3, not the four raw sources. This module acts
   on it and does not decide it, which is what 7.3 requires.

A4 _self CLEAR MEANS ENTRY K SURVIVES. backend_interfaces 5 says
   clear means "the naming instruction completed and everything
   after it is squashed", so the entry holding it survives and
   allocation restarts at K+1. Set is the trap case, the
   instruction is squashed, and allocation restarts at K. 5.5 R1
   states the two targets without saying which maps to which; this
   is the only mapping consistent with section 5's prose.

A5 fetch_ptr REWINDS ONLY WHEN AHEAD of the new head. 5.5 R1 says
   it "rewinds with it, since FQ-1 forbids fetch_ptr running ahead
   of alloc_ptr" -- the justification is FQ-1, so the action is
   required only where FQ-1 would otherwise break. A fetch_ptr
   behind the new head still has live entries in front of it and
   pushing it forward would skip them.

A6 THE COMMIT PAYLOAD QUALIFICATION IS NOT HERE. FE-11 says at
   most one RAS operation per entry; it does not say every entry
   has one. ftq_commit issues commit_step_val for each entry it
   frees and ftq_entry qualifies it where bp_ras_snapshot_t is
   read, because that is where the is-call/is-ret fact lives.
   Naming the port commit_step_val rather than ras_commit_val
   records that it is the walk step, not the qualified RAS commit.

A7 A REGISTERED WALK END is the right reading of the watermark. A
   watermark states a fact about architectural retirement and that
   fact does not expire when the port deasserts. This is what
   makes a multi-entry jump, a stalled watermark and a mid-walk
   deassert one behaviour instead of three special cases.

## Decisions made not explicit in the prompt

D1 ALLOCATION IS HELD ONE ENTRY SHORT OF THE 5.1 FULL CONDITION.
   THIS IS A DEPARTURE FROM ftq_decisions.md 5.1 AND IS THE MOST
   IMPORTANT ITEM IN THIS REPORT.

   5.1 gives full as alloc_ptr[5:0] == commit_ptr[5:0] with the
   generation bits differing, which is 64 live entries.
   bkend_ftq_commit_idx is FTQ_IDX_BITS wide and carries NO
   generation bit, so ftq_commit must reconstruct one against
   commit_ptr. With 64 live entries there are 65 distinct entries
   a held watermark could name -- the 64 live ones and the one
   just committed -- and 6 bits cannot separate 65 values.

   Concretely, with commit_ptr at 5 and alloc_ptr at 69:

     a held watermark of 4 is the LAST ENTRY ALREADY COMMITTED,
     still on the port because nothing new has retired. Section 6
     promises that repeating a watermark is harmless.

     a watermark of 4 is ALSO entry 68, the newest live entry, if
     the backend has just retired the whole queue.

   The two are bit-identical and demand opposite responses.
   Accepting frees 63 live entries and issues 63 false RAS
   commits. Rejecting deadlocks the second case: a full FTQ
   predicts nothing, so nothing further enters the backend and the
   watermark never advances again. Neither response is safe.

   THE STATE IS REACHABLE ON NORMAL TRAFFIC, not a corner. After a
   walk completes the FTQ refills while the backend works through
   what it already has; if it reaches full before retiring one
   more FTQ block, this is exactly the state. That is ordinary
   behaviour for a decoupled front end.

   Holding allocation at FTQ_DEPTH-1 removes the 65th value. A
   held stale watermark then always reconstructs to an age of
   FTQ_DEPTH, which exceeds the live window at every occupancy and
   is always rejected. The cost is one entry of 64, about 1.6% of
   run-ahead. Test group G of tb_ftq_commit drives the state and
   checks both halves: the held watermark is inert, and a real
   advance still commits the entire queue.

   The limit is a single named localparam in ftq_ptr.sv with the
   argument written out at its declaration, and property Q3 fires
   if it is ever reverted. Reverting it is one line the day
   bkend_ftq_commit_idx carries a generation bit.

   I did not edit any planning document. Section 5.1 should be
   corrected; the recommended text is in Deferred Work.

D2 RC_UNSPEC STOPS THE WALK AS WELL AS SUPPRESSING NOTHING.
   RC_UNSPEC performs no restore (U5), so by the letter of 5.4 it
   does not suppress. But U3 squashes every entry, including the
   ones between commit_ptr and the walk end that the walk had not
   reached, so there is nothing left to walk to. The walk end is
   snapped back to commit_ptr and no step is taken that cycle.

   Taking the step would be a pointer overrun rather than a wasted
   commit: the end snaps to the current commit_ptr while
   commit_ptr moves to commit_ptr+1, leaving an age of -1 and a
   walk of 127 entries. This was a real defect in the first draft
   of ftq_commit.sv, caught before delivery, and property C4 now
   guards it.

   THE INTERACTION IS NOT SPECIFIED ANYWHERE. See Deferred Work
   item 3: the literal reading of U3 discards RAS commits for
   entries that had already architecturally retired. U5's argument
   that the RAS is self-correcting from committed state covers it,
   and RC_UNSPEC is reset and debug-mode entry where the whole
   picture restarts, so the literal reading is implemented. It is
   flagged rather than assumed correct.

D3 ftq_commit BOUNDS ITS WALK BY alloc_ptr. This is the second
   crossing between the modules and it is not in 7.2. See Problem
   3 below.

D4 SVA WAS BOUND FOR BOTH MODULES, not only for FQ-1. The
   Constraints permit and encourage it for FQ-1; the commit rules
   are the same class of invariant and cost four more properties.
   Both files bind by MODULE name per TD#109.

D5 FTQ_PTR_BITS IS A MODULE PARAMETER, not a localparam, because
   it appears in port widths. It is a named width and not a knob;
   the comment at its declaration says so. See Deferred Work
   item 1.

## PROBLEM 3 -- the split

THE BOUNDARY HELD. Neither module reaches into the other's advance
decision. Each pointer has exactly one writer and the other module
reads it through a port, which is the partition rule of 7.1.

WHAT ACTUALLY CROSSES, in both directions:

  commit_ptr  ftq_commit -> ftq_ptr
  alloc_ptr   ftq_ptr    -> ftq_commit

THE HYPOTHESIS IS CORRECT THAT THE SPLIT WORKS AND SLIGHTLY WRONG
ABOUT WHAT CROSSES. It anticipated "the pointer values needed for
the full condition and the FQ-1 invariant", which is what crosses,
but 7.2 states the crossing as one-directional: "ftq_ptr reads
commit_ptr as an input to compute full. One writer, one reader, no
shared state." Two things are missing from that sentence.

FIRST, ftq_ptr NEEDS commit_ptr FOR TWO THINGS, NOT ONE. Besides
full, it needs it to reconstruct the wrap generation of
bkend_ftq_redir_idx, which is FTQ_IDX_BITS wide and carries no
generation bit. The named entry lies at or after commit_ptr by R2,
so an index below commit_ptr's low bits belongs to the next
generation. Without commit_ptr a rewind across a wrap goes to the
wrong entry -- test D12 of tb_ftq_ptr is the case: with commit_ptr
at 60 and alloc_ptr at 68, index 2 must rewind to 7'h43 and a
module reading the index literally rewinds to 7'h03, 64 entries
wrong. This is not an extra port, it is a second use of the one
7.2 already names, so the boundary is unaffected.

SECOND, THE CROSSING IS BIDIRECTIONAL. ftq_commit reads alloc_ptr,
and 7.2 does not mention it. It is used for one thing: bounding the
walk end to the live window. Two consequences follow, and the
second is why it is not optional.

  It rejects a watermark past alloc_ptr. Against a working backend
  that cannot happen -- R2 makes it the backend's obligation and
  5.5 R2 says the FTQ does not arbitrate it -- so on its own this
  is only defensive, and it turns FQ-1 from a contract on the
  backend into an invariant of this RTL for one compare.

  It is also what rejects the held stale watermark of D1. That is
  not defensive; it is the ordinary case. Without alloc_ptr,
  ftq_commit has no way to tell a repeated watermark from a
  forward one, and section 6's promise that repetition is harmless
  cannot be met.

So the honest statement of the boundary is: each module owns its
own pointers and reads the other's, and neither can be built
without the other's value. That is still one writer and one reader
per pointer and still no shared state, so the partition rule holds
as stated. What does not hold is 7.2's implication that the
dependency runs one way.

IF EITHER MODULE HAD NEEDED THE OTHER'S ADVANCE DECISION -- not its
value -- the split would have been wrong. Neither does. ftq_ptr
does not know whether ftq_commit stepped this cycle and does not
need to; it reads the resulting pointer. ftq_commit does not know
whether an allocation was accepted; it reads the resulting pointer.
The suppression rule, which 7.2 gives as the reason commit_ptr's
advance is not a local decision, turns out to be entirely local
once the redirect is an input: ftq_commit decides suppression from
redir_val and redir_cause without consulting ftq_ptr at all.
