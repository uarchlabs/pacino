# Task Overview

TD#132 and TD#137. Both are stored targets reconstructed against
something they should not need, both are in the BPU, and both change
testbench fixture encodings, so they run together.

TD#132: the ITTAGE target field holds VA[38:1] and the cluster
supplies bits 40:39 by extension. No extension rule is right for
both a V=1 guest physical address and a V=0 kernel address, and a
wrong entry is sticky because the update writes back the bits the
entry already holds. Ruled session-073: STORE THEM. The field
becomes VA[40:1] and no rule remains.

TD#137: the FTB jump target is a displacement from the region base.
Ruled session-073: every target is a displacement from its own
instruction, so the jump target is measured from the jump PC, as
BP-110 made a conditional target measured from the branch PC.

## Background
Ruled session-073, both by Jeff.

TD#132: the ITTAGE target field holds VA[40:1].
IT_MAX_TGT_WIDTH = 40 and IT_TBL_TGT_WIDTH is 40 for every tagged
table. Bit 0 is always zero at 2-byte granularity, so the
reconstruction is {stored, 1'b0}. NOTHING IS INFERRED: no sign or
zero extension anywhere in the path. This reverses the session-070
pin, which held the width to keep an entry size and not because
predictor storage was tight. Expected cost 2 bits x 2048 entries x
2 banks = 8,192 bits; confirm against IT_TBL_ENTRIES and
IT_TBL_BANKS rather than taking it from here.

ittage_pred_meta_t carries TWO targets per slot, ittage_prm_tgt and
ittage_alt_tgt, so it goes 143b -> 147b and bp_ftq_meta_t 421b ->
425b. The fast-path FTQ entry carries no ITTAGE target and does not
move. ftq_entry_formats.md records the arithmetic; it is a planning
document and is NOT edited here.

The entry field order is VALID, CTR, USE, EPC, TGT, TAG from LSB up
(ittage_table_entry_formats.md), so only TAG shifts. The merged
CTR + USE write of ittage_cntrl_decisions.md is below TGT and its
mask is unaffected; the merged CTR + TGT write is not.

TD#137: the FTB jump target is a displacement from the JUMP PC,
which is the region base plus the jump field's stored position,
exactly as BP-110 made a conditional target a displacement from the
branch PC (ftb_decisions.md 4.6 O-1, 4.2). FTB_JMP_TGT_BITS stays
21; only the base changes.

## ITTAGE entry and array widths
Entry = VAL 1 + CTR 3 + USE 2 + EPC 2 + TGT + TAG(t). Elaborated with
tools/bin/verilator 5.048 from the packages:

| Table | TAG | entries | before (TGT 38) | after (TGT 40) |
|-------|-----|---------|-----------------|----------------|
| IT1   |  8  |   256   | 46+8  = 54      | 48+8  = 56     |
| IT2   |  8  |   256   | 46+8  = 54      | 48+8  = 56     |
| IT3   |  9  |   512   | 46+9  = 55      | 48+9  = 57     |
| IT4   |  9  |   512   | 46+9  = 55      | 48+9  = 57     |
| IT5   | 11  |   512   | 46+11 = 57      | 48+11 = 59     |

TGT [45:8] -> [47:8]; TAG starts at 46 -> 48 (only TAG shifts).

Array total. ittage_table holds two RAM copies (u_ram_s0, u_ram_s1,
one per prediction slot), each of 2**IDX = IT_TBL_ENTRIES entries
split into IT_TBL_BANKS = 2 banks of half depth. Total entries per
copy = 256+256+512+512+512 = 2048.
- Before: per copy 54*256*2 + 55*512*2 + 57*512 = 113,152 bits;
  x2 copies = 226,304 bits.
- After:  per copy 56*256*2 + 57*512*2 + 59*512 = 117,248 bits;
  x2 copies = 234,496 bits.
- Delta 8,192 bits = 2 bits x 2048 entries x 2. MATCHES the ruling's
  8,192. Note the x2 is the two per-slot RAM copies, not
  IT_TBL_BANKS: the banks divide a copy, they do not duplicate it.
  The ruling's "2 banks" wording gives the right number for a
  different reason.
