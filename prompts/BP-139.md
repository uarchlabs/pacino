# Task Overview
TD#179, first of two tasks. Requirement (Jeff, 2026-10-18): every
branch is predicted, at every slot count. NUM_PRED_SLOTS sets how many
branches one prediction block carries, which is prediction bandwidth
into the FTQ. It does not decide whether a branch is predicted.

Two defects at NUM_PRED_SLOTS = 1, found by an interactive IA session
on 2026-10-18 (tree 0599061):

D1: a conditional the FTB holds in br1 is in no slot. The block's
predicted path runs past it as if it were not taken, so it is never
predicted. BP-138 fixed the same fault for the jump field only.

D2: when that conditional resolves, ftq_resolve places it in slot 0,
which holds the first conditional, and TAGE, SC, LP and ITTAGE are
trained with the first conditional's metadata. The same thing happens
at two slots to any branch the entry does not hold behind two
occupied slots.

This task builds the cluster cut for any branch the FTB reports and no
slot carries (option A), and stops table-predictor training through
another branch's slot (item C). BP-140 follows with per-start FTB and
uBTB entries and the block split at update.

## Hypothesis
D1 is a narrow cut condition: w_jmp_cut_p2 tests the FTB jump field
only, so a conditional the FTB reports in a field no slot reads leaves
the block end at the FTB's stored end. D2 is the BP-119 placement
rule: a position that names no slot is trained from the metadata of
whatever slot place_slot returns, including a slot that holds a
different branch.

## Background
From the IA session of 2026-10-18 (tree 0599061; the tree is now
138637d, with no RTL change expected between the two):

D1, the unslotted conditional.
- bp_cluster.sv, about 1657-1664: slot gs reads FTB br0 when gs == 0,
  else br1. At one slot only br0 is read. ftb_cntrl.sv, about 686-692,
  drives br1 at every slot count.
- ubtb.sv header, about 37-39: at one slot only the br0 field is
  reported.
- bp_cluster.sv p2_class_comb, about 1033-1040: w_jmp_cut_p2 is the
  FTB jump valid with every slot holding a conditional. p2_succ_comb,
  about 1103-1110: w_pft_p2 takes w_jmp_pc_p2 on the cut, else the
  jump end, else the FTB stored end. A visible br1 with no slot sets
  nothing, so the path runs past it as not taken.
- The FTB has exactly two conditional fields and one jump at every
  slot count (ftb_decisions.md 4). So the cut can only reach a branch
  the FTB stores: at one slot, br1 and a jump behind br0; at two
  slots, only a jump behind two conditionals (BP-138). A third
  conditional at two slots is never stored. It is BP-140's split and
  is out of scope here.
- ftb_decisions.md 3 records the split as NOT BUILT and says a second
  conditional at one slot is "still never reported (BP-128 D2)".

D2, training through another branch's slot.
- ftq_resolve.sv place_slot, about 283-294: a position naming no slot
  goes to the lowest slot that is free or at or after its position,
  else the last slot. At one slot, with slot 0 holding a conditional
  at a lower position, the result is slot 0.
- The header (BP-119) says a placed branch is trained as a mapped
  branch with no R2 suppression. The update carries slot 0's table
  index, tag and metadata, so TAGE, SC, LP and ITTAGE write the second
  branch's outcome into the first branch's entries. TAGE is indexed by
  block start PC per slot (bp_cluster.sv w_tage_pred_inp_p0), so this
  is not a shared entry two branches can both use: the second branch
  is never predicted from that start.
- The placed slot is also written into the FTQ entry (rsv_wr_*,
  ftq_entry.sv about 352-353), replacing the occupant. The backend
  resolves out of order, so the occupant can resolve after this write.
  By then its position no longer maps, and it is placed in turn.
- At two slots the same placement happens to any branch the entry does
  not hold that sits behind two occupied slots.

Observed effect, fd09_tage in fe_demo at one slot (2026-10-17 run).
Block at 0x8000_0008: B at halfword 3, the loop back edge at 7.
- On 101 of 256 iterations (B predicted not taken, B not taken) the
  back edge is unpredicted, mispredicts at the backend (redirect to
  0x8000_0008), and is placed in slot 0 with B's metadata.
- TAGE allocations: 209 at one slot (B 144, back edge 65), against 65
  at two slots (B 64, back edge 1).
- The back edge's slot-0 updates form a separate row of the fd09
  use_alt_on_na table (20 T2-over-T1, 10 T3-over-T2, 1 inc, 18 dec),
  all made with B's metadata.
- The split of the 209 vs 65 gap between wrong-slot training and the
  extra backend mispredicts was not measured.

fd04 at one slot (BP-138): the BP-138 jump cut costs one p2 redirect
per pass, because the uBTB's p1 end steps over the jump. Whether the
FTB and uBTB update path ever writes the cut end, or whether another
start of the same region overwrites it (the shared pftAddr,
ftb_decisions.md 4.6, TD#168), is not established.

XiangShan comparison (xiangshan/scala, NewFtq.scala FTBEntryGen and
Tage.scala). For information only; this task does not read xiangshan/.
XiangShan keeps no branch stored in an entry that no slot can carry.
A new branch is inserted with always_taken set, and TAGE does not
train a branch while that bit is set, so a branch's first execution
does not train through another slot's metadata. Item C gets the same
protection without new FTB state.
