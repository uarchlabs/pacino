## Background

Commit 9200b37 reshaped ubtb_upd_t. It no longer carries br_type or
carry. It now carries valid, pc, is_br, br_idx, br_taken, target,
pos, is_jmp, jmp_target, is_call, is_ret, is_jalr and pft_addr:
thirteen members mirroring the FTB update port, so one set of
resolved facts forms both updates.

bp_cluster.sv still drives the old shape. Its update fan-out reads
ubtb_upd_u0[gs].br_type and .carry, neither of which exists, and
forwards only six members onto w_ubtb_upd_u0. Verilator resolves the
missing br_type read to zero, which decodes as COND, so if the lint
error were cleared by re-adding the field rather than rederiving the
type, every update channel would classify as conditional, ITTAGE
would never be updated, and the uBTB would accept NO_BRANCH updates.
The type must be rederived, not restored.

ubtb.sv already implements the decode this needs, in its jmp_br_type
function. Reuse that arm order.

The uBTB also gained an output blk_p1 of type ubtb_blk_t, carrying
the entry hit and the reconstructed block fall-through. Hit is now
reported once per lookup; a pred_p1 slot's own valid bit says only
whether that slot carries a branch. bp_cluster.sv does not connect
blk_p1 at all and still infers the hit from a slot valid bit.
ubtb_pred_t also gained pos, which bp_ftq_slot_t now has a field
for.

Separately, the FTQ slow path has no producer. bp_ftq_meta_t holds
the state each predictor needs to train and cannot recompute at
resolution, and bp_cluster declares no port to write it. Without
those ports the update path cannot work at all: tage_upd_inp_t
embeds tage_pred_meta_t, ittage_upd_inp_t embeds
ittage_pred_meta_t, and sc_upd_inp_t embeds sc_pred_meta_t, and
those values exist only at predict time.

blk_p1.pft_addr is the uBTB's block fall-through.
ubtb_interfaces.md calls it authoritative for the cluster when no
slot is taken. Its place is the p1 successor operand of the p2
redirect comparison. That comparison reduces the p1 view and the p2
view of a slot to one quantity, the address fetched after that slot,
and redirects when they differ. Both sides currently use the FTB
fall-through, which masks the case the comparison exists to catch: a
block whose boundary the FTB places somewhere the uBTB did not.
blk_p1.pft_addr reads zero on a uBTB miss, so it needs a default.

bp_arb_spec.md 6.1 and TD#91/TD#92 stage the SC prediction PC and
the low ten bits of phr p0 to p2, because SC indexes at p2 the block
requested at p0. The three SC index folds are connected live to
bp_history, which advances whenever a branch is predicted, so at p2
they describe history newer than the block SC is indexing. Same
class of signal, same staging.

tb_bp_pkg.sv computes SLOT_BITS and ENTRY_BITS as localparams from
hand-written sums and asserts them against $bits. SLOT_BITS has no
term for bp_ftq_slot_t.pos. That check was added by BP-083 for
exactly this purpose and is doing its job.

The packing test in that file drives every field of a struct, copies
it whole, and checks read-back and cross-slot independence. Three
things the package gained are not driven by it: bp_ftq_slot_t.pos,
ftb_pred_meta_t, and the bp_ftq_meta_t ftb member.

ftq_bpu_interfaces.md sections 4, 6 and 7 are authority for the
prediction, redirect and metadata port groups.

### T1  ftb_pred_meta_t width check          (requirement 17, NEW)
- Rules: ftq_bpu_interfaces.md 7.3, ftb_pred_meta_t field list.
- Setup: none. $bits is evaluated from the type; fmeta_a need not
  be driven.
- Stimulus: compare $bits(fmeta_a) against localparam
  FTB_META_BITS = 1 + FTB_WAY_BITS + FTB_BR_POS_BITS, summed from
  the struct's own field widths rather than from $bits of the type,
  so the check is independent of the thing it checks.
- Expected: 6 bits (1 + 2 + 3).
- Criterion: $fatal on inequality. Mutation M2 confirms it fires.

### T2  bp_ftq_meta_t width check            (requirement 17, NEW)
- Rules: ftq_bpu_interfaces.md 7, bp_ftq_meta_t member list.
- Setup: none.
- Stimulus: compare $bits(meta) against localparam META_BITS, the
  sum of $bits of the four predictor member TYPES plus
  FTB_META_BITS. Summing the predictor members by type rather than
  by field keeps this check sensitive to a member being added to or
  removed from bp_ftq_meta_t, while their own field widths stay
  checked where those types are checked.
- Expected: 420 bits.
- Criterion: $fatal on inequality. Mutation M3, which drops the
  bp_loop_meta_t term, confirms it fires (got 420, want 340).

### T3  bp_ftq_slot_t width check         (requirement 16, CHANGED)

  in-block position on the fast path.
- Setup: none.

## Assumptions made not explicit in the prompt

1. Requirement 11 says "the block-aligned start PC plus
   FTB_BLOCK_BYTES" without naming an alignment width. The Makefile
   and the package give no FTB offset-bits parameter, so a
   file-local named parameter was added to bp_cluster.sv:
   BLK_OFF_BITS = $clog2(FTB_BLOCK_BYTES). No literal is used. The
   uBTB and the FTB describe the same block
   (UBTB_BLOCK_BYTES = FTB_BLOCK_BYTES), so one width serves both.

2. The p1 fall-through, and therefore the miss default, is scalar
   per lookup, not per slot: ubtb_blk_t is entry-scoped and one uBTB
   entry describes one block. Both slots' p1 successors take the
   same fall-through when not taken. This matches blk_p1.pft_addr
   being a single value.

3. Requirement 8 says bpu_meta_val_p2 "follows the p2 stage valid".
   That is read as r_val_p2 directly, not r_val_p2 qualified by
   ftb_valid_p2. The metadata write is unconditional per entry the
   same way the p1 allocation is: an entry whose FTB lookup was not
   valid still needs its slow path written.

4. The p3 metadata group is driven from r_val_p3 and r_idx_p3, the
   same pair the p3 redirect group uses. Requirement 10 names no
   separate valid source and states only that the group asserts
   whether or not SC is enabled, which r_val_p3 satisfies since it
   carries no sc_enable term.

5. The loop metadata is presented for slot 0 only. Requirement 8
   calls it "the registered p1 loop result"; the binding decisions
   say slots above 0 are driven to zero. Written as
   (gs == 0) ? lp_to_meta(r_lp_pred_p2) : '0.

## Decisions made not explicit in the prompt

1. The branch-type rederivation (requirement 2) is written as a
   module-scope automatic function, upd_br_type, called from the
   generate loop's continuous assign. The arm chain is expressed as
   if/else-if in the same order the requirement gives, matching
   ubtb.sv jmp_br_type. A nested-ternary continuous assign would
   have expressed the same logic but would not have read as the same
   decode. The generate-loop style rule is preserved: the loop body
   still holds continuous assigns only, and the update fan-out still
   avoids always_comb for the stl_sequent reason the file header
   gives.

2. The lp_pred_t to bp_loop_meta_t map (requirement 9) is likewise a
   module-scope function, lp_to_meta, with one assignment per field.
   Its comment states explicitly that a bit-level recast would be
   wrong, so a later reader does not "simplify" it.

3. Requirement 6's site. Only one site in bp_cluster.sv infers an
   entry hit from a slot valid bit, and it is NOT the selection mux
   arm: the binding decisions fix that arm ("else uBTB when the slot
   is valid"). The site is the loop_pred-wins arm's target gate. See
   Other Notes for the full enumeration and the reasoning.

4. The new metadata ports are grouped in the port list under
   comments naming ftq_bpu_interfaces.md 7.1 and 7.2 rather than
   under a bare "section 7" label, because bp_cluster.sv already
   carries a "section 7: update channel" comment for what the
   interfaces document numbers as section 8. That pre-existing
   mislabel was left untouched rather than silently corrected; it is
   outside the requirement 27 header scope. Recorded under Deferred
   Work.

5. tb_bp_pkg.sv drives meta = '0 before the requirement 20 packing
   test. This is required, not stylistic: driving only meta.ftb
   leaves the other 414 bits undriven and Verilator v5.048 raises
   UNDRIVEN on the partially driven signal, which is an error under
   the project -Wall. Zeroing first also satisfies the CLAUDE.md
   self-contained-test rule that start state be established rather
   than inherited.

## RVA23 compliance risks and gaps noticed

None introduced by this task. The branch-type rederivation preserves
the RVA23 call/return identification the RAS depends on: a return is
also a JALR so is_ret is tested first, and a call is indirect when
is_jalr is also set, matching the RISC-V link-register conventions
(rd/rs1 in {x1, x5}) that the resolution path encodes into those
bits. The arm order is identical to ubtb.sv jmp_br_type and to the

diverge.

generate the IT5 folds ittage.sv consumes, so those fields read zero
(TD#102). This weakens indirect-branch prediction accuracy but is not
an architectural compliance issue.

### Requirement 6: every site changed

The cluster reads a pred_p1 slot valid bit in exactly two places.
Both were examined; one changed.

1. p1_form_comb, the loop_pred-wins arm target gate. CHANGED.

   Was:
     w_slot_p1[s].target = r_ubtb_pred_p1[s].valid
                             ? r_ubtb_pred_p1[s].target : '0;
   Now, via a named term:
     ubtb_slot_hit       = r_ubtb_blk_p1.hit
                         & r_ubtb_pred_p1[s].valid;
     w_slot_p1[s].target = ubtb_slot_hit
                             ? r_ubtb_pred_p1[s].target : '0;

   This is the site the Background describes. The quantity the gate
   needs is "does the uBTB describe this slot", which under the
   reshaped interface is two terms: the entry hit, reported once per
   lookup on blk_p1.hit, and the slot's own valid bit, which now
   says only that the slot carries a branch. The hit term is
   explicit rather than implied.

   Behaviourally this is a no-op today and is intended to be:
   ubtb.sv drives pred_p1 entirely to zero on a miss, so a set slot
   valid bit already implies a hit. The change makes the dependency
   visible so a future ubtb.sv that stops zeroing on miss cannot
   silently break the cluster. It does not count against the "no
   behavioural change beyond 11, 12 and 14" constraint.

2. p1_form_comb, the selection mux arm condition
   (else if (r_ubtb_pred_p1[s].valid)). NOT CHANGED.

   The binding decisions fix this rule verbatim: "loop_pred when
   lp_pred_is_loop, else uBTB when the slot is valid, else the slot
   carries no prediction." The slot valid bit is the correct and
   specified term here -- it selects whether the slot carries a
   prediction, which is a slot-scoped question, not an entry-scoped
   one. Substituting blk_p1.hit would make a hit with no valid slot
   produce a prediction, which ubtb_interfaces.md explicitly calls a
   legal state with no branch.

blk_p1.hit is additionally read by new logic in requirement 11, the
p1 fall-through selection. That is a new consumer, not a changed
site, and is listed here only so the full set of blk_p1.hit readers
is on the record.

### Requirement 12: which cases newly redirect

The p2 redirect compares the p1 view and the p2 view of a slot,
each reduced to the address fetched after that slot. Only the p1
operand changed:

  was:  p1_succ = r_slot_p2[s].taken ? r_slot_p2[s].target
                                     : w_ftb_pft_addr_p2;
  now:  p1_succ = r_succ_p1_p2[s];

where r_succ_p1_p2[s] is the staged form of

  w_succ_p1[s] = w_slot_p1[s].taken ? w_slot_p1[s].target
                                    : w_pft_p1;
  w_pft_p1     = r_ubtb_blk_p1.hit
                   ? r_ubtb_blk_p1.pft_addr
                   : block_aligned(r_pc_p1) + FTB_BLOCK_BYTES;

The taken arm is unchanged in value: r_slot_p2[s] IS the staged
w_slot_p1[s], so r_slot_p2[s].target and w_slot_p1[s].target are the
same number. Nothing about a p1-taken slot changes.

The whole behavioural change is therefore confined to the p1
NOT-TAKEN arm, where the operand moved from the FTB fall-through to
the p1 fall-through. Newly redirecting cases:

1. p1 slot not taken, uBTB HIT, and blk_p1.pft_addr differs from
   w_ftb_pft_addr_p2. This is the case the comparison exists to
   catch and that the old code masked: a block whose boundary the
   FTB places somewhere the uBTB did not. Concretely, the uBTB
   recorded a block ending at one instruction and the FTB, which is
   authoritative, ends it at another -- for instance because the FTB
   knows a block-terminating jump the uBTB entry has not yet
   recorded, or because a stale uBTB entry still carries the old
   block end after a code change. Previously both sides of the
   comparison read w_ftb_pft_addr_p2 and compared equal, so the
   front end kept fetching from a boundary the FTB had already
   contradicted. Now it redirects to the FTB fall-through.

2. p1 slot not taken, uBTB MISS, and the block-aligned start PC plus
   FTB_BLOCK_BYTES differs from w_ftb_pft_addr_p2. On a miss the
   cluster's p1 view is "the whole block, no branch", so its
   successor is the next sequential block. When the FTB then reports
   a block that ends early -- any block containing a branch the uBTB
   had not recorded -- the two disagree and a redirect fires. This
   is correct: the p1 stage genuinely fetched past the real block
   end and must be corrected.

3. p1 slot not taken, p2 slot TAKEN. Both before and after, a
   redirect fires whenever the p2 taken target differs from the p1
   successor. The p1 successor changed value, so the boundary case
   flips: previously no redirect fired when the p2 taken target
   happened to equal w_ftb_pft_addr_p2; now none fires when it
   equals the p1 fall-through instead. This is a degenerate case (a
   taken branch whose target is exactly the block end) and is listed
   for completeness rather than as a real behaviour change.

Cases that do NOT newly redirect: any slot taken at p1 (arm
unchanged, see above); any case where the uBTB and the FTB agree on
the block boundary, which is the common case on a warm uBTB; and
everything at p3, whose comparison and operands are untouched.
