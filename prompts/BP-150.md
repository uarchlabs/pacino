### Corrections to the IA's report

1. IT WAS A CORRECTNESS DEFECT, not "a performance loss, not an
   architectural one" (RVA23 risks). In the harness and tb_fe_top the
   backend compares the fetched stream with the program, so a skip
   shows up as a mispredict and is repaired. A real backend does not
   know the program: it resolves the branch against the entry's stored
   prediction. After the p3 write that prediction is not taken, the
   branch is not taken, so nothing mispredicts, and the skipped
   instructions are never executed. TD#205's CORRECTNESS label was
   right.

   after a conditional as a mispredict by design

   FTQ's own prediction never fails a check. sc_nored had to read the
   ibuf write port to see it. That is a verification gap of its own
   (see TDs below).

## Hypothesis
The p3 successor is right and the defect is in the flush. W3, IB-12,
IB-13 and IBUF-8b all rest on one claim: a p2 or p3 redirect fires
before the entry it names has been fetched. FQ-1 orders the pointers
but does not enforce that claim. When fetch has caught up with
allocation, entry K can be fetched, and its block truncated at the
branch predicted taken at p2, before SC reverses that branch at p3.
The p3 flush at K then does not give back the instructions after the
branch.

THE SKIP RULE
- A REVERSAL is a p3 slot write for K (ftq w_ok_slot_p3), with K not
  squashed by a backend or predecode redirect that cycle, in which a
  reachable slot is taken in the p2 view and not taken at p3. B is
  r_pc_p3 + 2*pos.
- The test: the first instruction written to the ibuf after B, B
  being the copy written from entry K, is not B+4.
- Undecided cases are not counted as skips:
  - clr: an ibuf clear (backend redirect) came first;
  - sq: entry K was reallocated first.
- All trace images are 32-bit words, so B+4 is the next instruction.

PROBLEM 2. THE CAUSE
- The skip arises at ftq_ifu.sv:267-288. In K's p3 cycle the request
  is formed from fetch_entry = r_arr[fetch_idx] (ftq_entry.sv:216).
- In that same cycle bp_cluster's p3 slot correction rewrites K's
  slots (ftq_entry.sv:328-332). But it raises bpu_redir_p3 only when
  w_succ_p3 != p2_succ (bp_cluster.sv:1345-1346), so no flush
  discards the stale request.
- The IFU truncates on taken_val/taken_pos (ftq_ifu_interfaces.md 4).
  Evidence: Problem 1 cases 1 and 2, and the table (all skips are
  noredir_iss).
- The Hypothesis's claim fails: K is never fetched before a p2 or p3
  redirect (p2i = p3i = 0 in all 12 runs).
- The premise that does not hold is in W3's own reason: "the
  correction changes taken_val and taken_pos ... a fetch issued
  against the old prediction would truncate in the wrong place". It
  assumes every such correction arrives as a redirect. A p3 slot
  correction with an unchanged successor is not a redirect, so no
  binding rule's text is false; W3, IB-12, IB-13 and IBUF-8b do not
  cover it.
- p2 is checked the same way and is never affected, in two forms:
  - a winning p2 redirect for an entry whose fetch request had been
    accepted: 0 in all 12 runs (p2i);
  - a p2 slot write for such an entry: 0 in all 12.
  - Structurally: a request for K is first presentable at p3, after
    K's p2.
