## Hypothesis

The status fields do not belong in bp_ftq_entry_t.

Every prior FTQ field discussion has been about which of the two
SRAMs a field lands in, and the framing of item 3 -- "bp_ftq_entry_t
carries no fetch state" -- carries that assumption forward. But
these are set by an event asynchronous to the fetch read and cleared
for a RANGE of entries in one cycle by a rewind. If that is right,
the answer is a third storage class rather than a wider entry, and
the entry totals do not move at all.

## Background

FE-U7 blocked item 1 and is resolved. ftq_decisions.md 5.6 solves
the stale-response problem for CLUSTER responses with a four-deep
in-flight shadow, and the question for item 2 is whether that
mechanism transfers to the IFU path. BP-100 built ftq_ftb_sched as a
standalone module, which is the precedent item 3 either follows or
departs from.

## Assumptions made not explicit in the prompt

- The partition of requirement 3 is derived from ONE rule: every
  piece of state has exactly one owner module, and everything else
  reads it through a port. The rule was chosen, not given. It is
  what makes ftq.sv structural rather than merely thin -- a top
  with no state of its own has nothing to decide.
- gen is written at allocation, which is ftq_ptr's event, but held
  in ftq_status with the other per-entry vectors. Storage class,
  not producer, decides the owner.
- ONE generation bit is sufficient because of a BOUND, not the
  encoding. A single bit fails if an index is reallocated twice
  while a writeback is outstanding, since the second toggle
  restores the original value. The IFU flush of
  ftq_ifu_interfaces.md 5 makes that unreachable: the only stale
  writeback surviving a redirect is one already presented in the
  flush cycle, and it arrives immediately. This is recorded in 6.1
  WITH ITS TRIGGER -- if the IFU flush contract changes so a
  writeback can survive arbitrarily long, the width must be
  revisited.

## Decisions made not explicit in the prompt

- THE STATUS FIELDS ARE FLOPS, outside both SRAMs, 192 bits. Three
  reasons, and the third decides it: the writeback arrives at an
  arbitrary time relative to the fetch read, so a bit inside the
  fast-path entry would be a read-modify-write of an SRAM already
  read every cycle; the commit walk and the next-PC hold test these
  ACROSS entries, and a flop vector reads whole; and a redirect
  rewind squashes every entry after an index and must clear their
  status in ONE cycle, which in SRAM is a walk that would have to
  finish before those indices could be reallocated.
- A TOGGLE, not the pointer's wrap bit. A rewind can reallocate an
  index within one wrap, where a wrap-derived value does not
  discriminate.
- THE THREE POINTERS SPLIT across ftq_ptr and ftq_commit, even
  though 5.1 presents them together. commit_ptr is the only one
  whose advance is not a local decision: 5.4 rate-limits it against
  the scalar RAS commit port, reads bp_ras_snapshot_t out of the
  entry to form the payload, and suppresses the advance whenever a
  redirect restore fires. ftq_ptr reads commit_ptr as an input to
  compute full.
- REDIRECT ARBITRATION IS IN ftq_npc. Four sources ordered by age
  (4.3), and the ordering answers one question: where fetch goes
  next. The winner IS the next-PC source. ftq_npc publishes it to
  ftq_ptr for the rewind and to ftq_status for the masked clear;
  those act on it, neither decides it.
- ftq_status is separate from ftq_entry because the storage class
  differs. Keeping them apart makes that structural rather than a
  comment.
- Grouped as ONE task file rather than three. BP-101 is the
  precedent: three items that were prerequisites for the same
  thing, so one task. Here the chain is tighter still -- item 2 was
  found by specifying item 1.
