## Context Comments
The FTQ has NUM_PRED_SLOTS update channels. Every predictor accepts
two per cycle except the FTB, whose update is 14 flat ports with no
slot dimension and NO ready. Presenting two in one cycle silently
loses one.

ftq_decisions.md 5.7 is the specification: the value classes in
5.7.2, the rule S1 to S6 in 5.7.3, and the five properties in 5.7.4.
IC-FTB-09 and G9 are resolved against it. FE-5a is the amendment that
permits the drop.

WHY A STANDALONE MODULE. The scheduler is FTQ logic and the FTQ does
not exist, but the scheduler does not depend on the rest of it: its
inputs are two resolution-derived update payloads and its output is
the cluster's existing update port group. Building it alone gets the
smallest FTQ module verified early, and gets the project's first
concurrent SVA written and bound while the logic is small enough that
the properties are obviously right.

## Hypothesis
The rule of 5.7.3 is implementable with one skid register and a
one-bit value function, and the five properties of 5.7.4 hold on it.
If a property cannot be written against the delivered ports, the
port list is wrong, not the property.

## Background
At the 8-issue target of CLAUDE.md, 15 to 20 percent branch density
gives 1.2 to 1.6 branch resolutions per cycle and every one writes
the FTB. One write per cycle is below that, and FE-5's original
no-drop guarantee turned the deficit into backpressure on resolution,
so a predictor training limit stalled the backend.

The fix is not more FTB ports. It is dropping the updates that do not
matter: a routine conf step on a branch that hit and predicted
correctly. Allocations and mispredict corrections are never dropped.

## Binding Previous Decisions
- ftq_decisions.md 5.7.3 S1-S6 is the rule. Implement it, do not
  re-derive it.
- FE-5a: LOW may be dropped, HIGH never. FTB path only.
- FE-6: updates reach a predictor in resolution order. The skid
  issues before anything newer.
- IC-FTB-16: slot 0 is the block's earlier branch, so slot-0-first
  is program order within an entry.
- The FTB is UNCHANGED by this task. No second write port, no
  banking, no wider payload. ftq_decisions.md 5.7.5 records those as
  escalations that need measurement first.

## Assumptions made not explicit in the prompt

- S1 is implemented as `is_br | is_jmp` on the flat payload rather
  than from a br_type port. 5.7.3 states S1 as "br_type is anything
  other than NO_BRANCH"; a resolved NO_BRANCH forms neither field,
  and bp_cluster.sv already qualifies its own FTB update exactly
  this way. Requirement 2's port list has no br_type, so adding one
  would have carried redundant information.
- `upd_rdy` is the scheduler's contribution to `ftq_bkend_rsv_rdy`,
  not the whole of it. The scheduler owns only the FTB reason for
  deasserting; the FTQ ANDs it with the others. The property reads
  the scheduler's port.
- n_pend_ftb and any_pend_high count the skid plus the PRESENTED
  FTB-bound channels, not the accepted ones. P5 constrains the
  ready, so counting accepted channels would make the property
  depend on its own conclusion.

## Decisions made not explicit in the prompt

- P4 CORRECTED, |-> to |=>, and ftq_decisions.md 5.7.4 updated.
  P1 asserts ftb_upd_valid_u0 with |=>, which requires a registered
  output; P4 asserted the same signal with |-> in the same cycle,
  which requires a combinational one. NO IMPLEMENTATION SATISFIES
  BOTH. This is not the failure mode the Hypothesis predicted -- it
  is not a port list problem, and no port list fixes it. The
  registered form was built, because P1 is also the better design:
  the scheduler is a pipeline stage, not a wire. P4's intent is
  unchanged.
- The five observation signals are PORTS on ftq_ftb_sched, not
  internal nets. The bind then reads only the port list and makes no
  hierarchical reference into the module. This costs seven output
  ports that no consumer reads.
- -Wno-SYNCASYNCNET on both ftq targets, per target rather than in
  VER_FLAGS, following lint_bp_cluster. rstn is an async reset on
  the flops and appears synchronously in every property's
  `disable iff (!rstn)`. That is structural to any module carrying
  both an async reset and concurrent SVA.
- --assert on both targets. Without it Verilator parses the
  properties and generates nothing. Recorded in the Makefile at the
  target, not left to the reader.
- NUM_UPD_CHAN rather than reusing NUM_PRED_SLOTS as the parameter
  name, so it does not shadow the package parameter and need
  -Wno-VARHIDDEN.
