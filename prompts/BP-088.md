## Background

BP-087 is abandoned. Its RTL work was correct and its Results
Capture records what was done; this task redoes that work rather
than building on it, because the tree may or may not carry the
BP-087 edit. Read bp_cluster.sv and determine which of the changes
below are already present before making any edit.

The uBTB now performs one lookup per cycle. One entry describes one
block. The two prediction slots are the two conditional branch
fields of that entry, and the block-terminating jump is reported in
the lowest slot carrying no valid conditional field.

Three things changed at the uBTB interface. ubtb_pred_t gained pos
and conf, and its carry field is now the entry fall-through carry
rather than a property of the slot target. A new output blk_p1 of
type ubtb_blk_t carries the entry hit and the reconstructed
fall-through; hit is reported once per lookup rather than per slot.
ubtb_upd_t was reshaped to mirror the FTB update port: it no longer
carries br_type or carry, and now carries is_br, br_idx, pos,
is_jmp, jmp_target, is_call, is_ret, is_jalr and pft_addr.

The package gained three things for the metadata path.
ftb_pred_meta_t is new and holds the FTB hit, way and jump position.
bp_ftq_meta_t gained an ftb member of that type. bp_ftq_slot_t
gained a pos field of FTB_BR_POS_BITS.

tb_bp_pkg.sv computes SLOT_BITS and ENTRY_BITS as localparams from a
hand-written sum of field widths, and asserts them against $bits of
the real structs. Neither sum has a term for the pos field, so the
bp_ftq_slot_t assertion fails: the measured width is 55 and the
expected value is 52. ENTRY_BITS derives from SLOT_BITS and carries
the same shortfall. That check was added by BP-083 for exactly this
purpose and is doing its job.

ftq_bpu_interfaces.md section 7 specifies the metadata write groups.
Section 4 specifies the p1 prediction. Both are authority.

## Binding Previous Decisions

- ubtb.sv, bp_structs_pkg.sv and bp_defines_pkg.sv are correct as
  they stand. Do not change them.
- The uBTB reports hit once per lookup on blk_p1.hit. A pred_p1 slot
  with valid = 0 on a hit means that slot carries no branch, which
  is a legal state; the successor is then the fall-through.
- The p1 selection mux rule is unchanged: loop_pred when
  lp_pred_is_loop, else uBTB when the slot is valid, else the slot
  carries no prediction. Slot 1 has no loop_pred producer and takes
  the uBTB prediction (TD#105).
- The metadata finalizes at two stages. The p2 group writes the
  tage, ittage, lp and ftb members of bp_ftq_meta_t; the p3 group
  writes the sc member. The two sets are disjoint so the FTQ never
  merges.
- The loop predictor finalizes at p1. Its result is registered and
  presented in the p2 group so the FTQ performs one slow-path write
  per entry.
- bp_ftq_meta_t is carried per slot. The array is declared at the
  port, not inside the struct.
- The FTB hit, way and jump position are scalar within the entry:
  the FTB indexes one entry per lookup and both slots come from it.
  The cluster writes the same values into every slot's copy.
- BUG-006: build from the tree. If a Context Loaded path does not
  exist, STOP and report it.

### Metadata write ports

7. Add the p2 metadata write group per ftq_bpu_interfaces.md 7.1:

```
   bpu_meta_val_p2                                      output
   bpu_meta_idx_p2     [FTQ_IDX_BITS-1:0]               output
   bpu_meta_tage_p2    tage_pred_meta_t   per slot      output
   bpu_meta_ittage_p2  ittage_pred_meta_t per slot      output
   bpu_meta_lp_p2      bp_loop_meta_t     per slot      output
   bpu_meta_ftb_p2     ftb_pred_meta_t    per slot      output
```

   TAGE and ITTAGE metadata are the predictor outputs passed
   through. The FTB metadata is built from ftb_hit_p2, ftb_way_p2
   and ftb_jmp_pos_p2, the same values written into every slot's
   copy. The loop metadata is the registered p1 loop result mapped
   from lp_pred_t to bp_loop_meta_t; the two carry the same field
   set under two spellings.

   loop_pred is single slot. Slots above 0 carry no loop state and
   are driven to zero, not to a copy of slot 0: copying would hand
   the FTQ loop-table coordinates belonging to a different branch.

   bpu_meta_val_p2 follows the p2 stage valid. bpu_meta_idx_p2 is
   the p2 stage FTQ index.

8. Add the p3 metadata write group per ftq_bpu_interfaces.md 7.2:

```
   bpu_meta_val_p3                                      output
   bpu_meta_idx_p3     [FTQ_IDX_BITS-1:0]               output
   bpu_meta_sc_p3      sc_pred_meta_t     per slot      output
```

   The SC metadata is the predictor output passed through.
   bpu_meta_val_p3 is asserted whether or not SC is enabled, so the
   entry's slow path is always complete.

9. Do not stage the TAGE or ITTAGE metadata to p3 to merge the two
   groups into one write. The groups write disjoint members and the
   FTQ writes each as it arrives.

## Assumptions made not explicit in the prompt

1. blk_p1 is registered p0 -> p1 the same way pred_p1 is.
   Requirement 2 says to register it "alongside the registered
   pred_p1 result", which names the group; this assumption is the
   reason it is the right group. Both outputs are combinational from
   pred_pc_p0 and both are consumed by the p1 selection mux, which
   reads the registered loop_pred result, so splitting them across
   the boundary would compare a p0-cycle hit against a p1-cycle
   slot.

2. The loop metadata is registered p1 -> p2 in the cluster's own
   stage register group, r_lp_pred_p2 <= w_lp_pred_p0, alongside the
   existing p1 -> p2 transfers. Requirement 7 says the loop result is
   "registered and presented in the p2 group" without naming the
   register.

3. The metadata payload ports are driven unconditionally, not gated
   on their group valid. The group's valid names the write; the
   payload is a don't-care when the valid is low. This matches how
   the p1 prediction and redirect output arrays are driven.

4. For requirement 11, "the same form as the existing checks" means
   the same $bits-against-a-localparam form, not that every member
   of bp_ftq_meta_t must be re-summed field by field. META_BITS sums
   the four predictor members by type and the ftb member by its own
   field widths. Rationale in Decisions item 5.

## Decisions made not explicit in the prompt

1. Update classification source. Requirement 5 specifies a
   structural decode in the FTB arm order with is_br outranking
   is_jmp; the concrete expression chosen is in Other Notes. It is
   placed in gen_slot as a continuous assign, where the old br_type
   read was, so the block-classification style of the file is
   unchanged.

2. w_upd_type_u0 stays a bp_br_type_e. Its three consumers --
   w_upd_any_u0, w_upd_cond_u0, w_upd_ind_u0 -- are unchanged in
   both expression and meaning, so the fan-out to TAGE, ITTAGE, SC
   and loop_pred is bit-identical to BP-085 for any input BP-085
   could also have seen. Only the producer of the enum changed. This
   is the smallest edit that satisfies the Constraints line freezing
   the other predictors' fan-out.

3. bpu_meta_lp_p2 for slots above 0 is driven to bp_loop_meta_t
   zero, not to a copy of slot 0, per the requirement 7 instruction.
   Zero reports lp_hit = 0 and lp_pred_is_loop = 0, which the update
   path reads as "no loop state for this slot". The port has a real
   driver, so the "every metadata output must have a producer"
   constraint is met; this is a driver, not a tie-off of a predictor
   output.

4. The FTB metadata is assembled field by field rather than by
   struct assignment, so the three source nets are visible at the
   assignment and a future width change fails loudly.

5. The lp_pred_t -> bp_loop_meta_t map is an always_comb block,
   meta_lp_comb, rather than a chain of continuous assigns: the
   thirteen assignments form no dependency chain but the block also
   has to zero the higher slots first, which is sequencing. It reads
   r_lp_pred_p2, a flop output, so it is nba_sequent and not subject
   to the CLAUDE.md stl_sequent hazard. The gating signal is named
   in the block's header comment, per the Constraints.

6. META_BITS sums tage, sc, lp and ittage by $bits of their types
   rather than by re-listing every field of each. Those four
   predictor metadata structs are each many fields wide and are
   checked field by field where their own types are defined; copying
   those lists here would duplicate them without adding coverage.
   The check's purpose is to catch a member added to or removed from
   bp_ftq_meta_t -- which it does -- and to catch a change to the new
   ftb member, which the hand-written FTB_META_BITS term does.

7. The existing "section 7: update channel" comment in the port list
   was left alone. ftq_bpu_interfaces.md numbers metadata as 7 and
   updates as 8, so the file's existing label is off by one, but
   correcting it is outside this task's scope. The new group is
   labelled "prediction metadata, BPU -> FTQ (interfaces 7)" so the
   two do not collide.

## RVA23 compliance risks and gaps noticed

None arising from this task. The change is microarchitectural
plumbing at the branch predictor boundary and touches no
architectural state, no CSR, no exception behaviour and no
instruction semantics.

One 8-wide-dispatch observation, recorded rather than raised as a
risk. The metadata ports are sized per prediction slot at
NUM_PRED_SLOTS, which is 2, matching the two conditional fields of
one FTB block. That is the block descriptor width, not the dispatch
width, so it does not cap the 8-instruction-per-cycle front-end
target. The front end sustains 8 instructions per cycle by fetching
one 32-byte block of 8 instructions, not by widening the slot array.

### Requirement 4 -- what became of blk_p1.pft_addr

It has no consumer. It is not tied off and is not read; it is
carried on w_ubtb_blk_p1 and registered into r_ubtb_blk_p1, so it is
available to the task that adds its consumer. No UNDRIVEN or UNUSED
warning results: the net is driven by the uBTB, and -Wno-UNUSED is
project-wide in VER_FLAGS.

There is exactly one place in the cluster where a p1 fall-through
would be consumed, and this task cannot use it. That place is the
p1_succ operand of the p2 redirect comparison in p2_succ_comb:

```
  p1_succ = r_slot_p2[s].taken ? r_slot_p2[s].target
                               : w_ftb_pft_addr_p2;
```

The not-taken operand is the FTB p2 fall-through. Per
ubtb_interfaces.md, blk_p1.pft_addr is "authoritative for the
cluster when no slot is taken", so on the merits this operand should
be the registered uBTB fall-through. Three reasons this task does
not make that change:

1. The task Constraints freeze it: "The redirect derivation ... stay
   as BP-085 left them." Changing an operand of the redirect
   comparison is a change to the redirect derivation, and a
   behavioural one -- it makes p2 redirects fire on cases that
   currently compare equal.

2. It is incomplete on its own. blk_p1.pft_addr reads 0 on a uBTB
   miss, and a miss is the common case at start-up. Substituted
   directly it would compare 0 against the FTB fall-through and
   assert a redirect on every miss. A correct version needs a
   miss-case default -- the block-aligned next block, r_pc_p1 +
   FTB_BLOCK_BYTES -- which is new logic, not a rewire, and is
   beyond "what the reshaped uBTB interface requires".

3. No p1 output port carries a fall-through to the FTQ.
   ftq_bpu_interfaces.md section 4 lists four p1 outputs --
   bpu_pred_val_p1, bpu_pred_idx_p1, bpu_pred_slot_p1,
   bpu_pred_ras_p1 -- and none is a fall-through or a successor. So
   there is no second candidate consumer to fall back on, inside the
   cluster or at its boundary.

### Requirement 5 -- update classification source

The structural decode, in the gen_slot loop where the old br_type
read was:

```
  assign w_upd_type_u0[gs] =
          ubtb_upd_u0[gs].is_br   ? COND
        : !ubtb_upd_u0[gs].is_jmp ? NO_BRANCH
        : ubtb_upd_u0[gs].is_ret  ? RETURN
        : ubtb_upd_u0[gs].is_call ? (ubtb_upd_u0[gs].is_jalr
                                       ? INDIRECT_CALL
                                       : DIRECT_CALL)
        : ubtb_upd_u0[gs].is_jalr ? INDIRECT_NONRET
        :                           DIRECT_UNC;
```

is_br outranks is_jmp, as the requirement specifies. The trailing
four arms are the FTB jump classification of p2_class_comb, arm for
arm, in the same order: is_ret first because a return is also a
JALR, then is_call split by is_jalr into INDIRECT_CALL and
DIRECT_CALL, then bare is_jalr as INDIRECT_NONRET, then DIRECT_UNC.
That is also the order of ubtb.sv's own jmp_br_type function, so
predict-side and update-side classification agree.

The source is the same set of resolved facts the FTB update fan-out
reads: w_ftb_upd_val_u0 is ftb_upd_valid_u0 & (ftb_upd_is_br_u0 |
ftb_upd_is_jmp_u0), the same is_br / is_jmp pair. The reshaped
ubtb_upd_t was made to mirror the FTB update port, so the two
fan-outs cannot diverge.

### The lp_pred_t to bp_loop_meta_t field mapping

Thirteen fields each, one to one, no field dropped and none
invented. Eleven names are identical; only the two iteration counts
are spelled differently:

```
  lp_pred_t (source)      bp_loop_meta_t (destination)
  ----------------------  ----------------------------
  lp_hit                  lp_hit
  lp_idx                  lp_idx
  lp_tag                  lp_tag
  lp_way                  lp_way
  lp_pred_is_loop         lp_pred_is_loop
  lp_pred_taken           lp_pred_taken
  lp_age                  lp_age
  lp_conf                 lp_conf
  lp_past_itr             lp_pst_itr    <- name differs
  lp_curr_itr             lp_cur_itr    <- name differs
  lp_curs                 lp_curs
  lp_curs_v               lp_curs_v
  lp_victim               lp_victim
```

Widths are identical field for field: both structs take lp_idx from
LP_IDX_BITS, lp_tag from LP_TAG_BITS, lp_way and lp_victim from
LP_WAY_BITS, lp_age from LP_AGE_BITS, lp_conf from LP_CNF_BITS, and
the three iteration values from LP_ITR_BITS. No cast is needed on
any assignment. The two structs differ only in field ORDER, which is
why the map is written field by field rather than as a bit-level
recast: lp_pred_t leads with lp_idx and bp_loop_meta_t leads with
lp_hit, so a straight $bits reinterpretation would scramble them.

The map is applied to slot 0 only. Slots above 0 are zeroed first in
the same block.
