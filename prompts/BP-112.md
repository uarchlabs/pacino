# Task Overview

TD#126 and TD#127. Both are in the FTQ, both are gates on the IFU,
and both reach ftq_ifu.sv, so they run together.

TD#126: the IFU flush index is wrong for a front-end redirect. A p2,
p3 or predecode redirect corrects entry K and K survives, so the IFU
must be flushed AT K and fetch K against the correction. The RTL
flushes at K+1 whenever _self is clear, which leaves a fetch of K
issued against the old prediction, truncating at the old taken_pos.
The BACKEND half of the same rule is correct and stays as it is.

TD#127: xlate_ptr is specified and not built. BP-107 completed the
FTQ as a three-pointer design before ftq_decisions.md 5.1 added the
fourth, and ftq_ifu.sv has no translation request group. The IFU
cannot be built against ftq_ifu_interfaces.md 4.1 until both exist.

## Claude.ai Assessment

trong task, and one finding changes the order of everything after it.

N1 is a correctness bug, not a performance one

In a redirect cycle the p0 request carries the pre-rewind alloc index, so the block at the redirect target is written to a squashed entry and never fetched. The next entry fetched holds target+32. That means the first 32 bytes of the corrected stream are skipped — instructions that should execute don't. It predates BP-112, it applies to backend redirects as well as front-end ones, and tb_ftq D9 never caught it because it checks only the index.

It also reaches TD#134. Wrong-path handling is being designed against a redirect path that currently loses the target block, so fixing N1 first means that session designs against correct behaviour.

I'd put this ahead of the IFU work and ahead of the remaining BPU items.

The finding I owed you from earlier

TD#138 -- a redirect and a request handshake in the same cycle.
Not ruled. As built since BP-106 for fetch_ptr, and extended to
xlate_ptr by BP-112 to match.

fetch_ptr. In a redirect cycle ftq_ifu still presents the section 4
request from the PRE-rewind fetch_ptr: ftq_ifu_req_val is
fetch_pending (ftq_ifu.sv:243) and is not gated by the redirect.
The entry fields are read at the old fetch_idx. If the IFU asserts
ftq_ifu_req_rdy, ftq_ptr ignores the handshake. The redirect branch
(ftq_ptr.sv:386-389) loads fetch_ptr with min(fetch_ptr, F) and
does not advance it. There are two cases.
- fetch_ptr was behind F. The request names a live entry. The IFU
  keeps it, because the flush applies first and the index is below
  F. The FTQ presents the same entry again next cycle, so it is
  fetched twice under the same generation tag.
- fetch_ptr was at or past F. The request names an entry the
  redirect squashes or rewinds to. For a p2, p3 or predecode
  redirect this includes K, read BEFORE the W1 correction lands,
  which is the TD#126 hazard in a single cycle.
xlate_ptr. The same rule. ftq_ifu_xlate_val is xlate_pending
(ftq_ifu.sv:218), presented at the pre-rewind xlate_idx with its
pc. ftq_ptr.sv:388 loads min(xlate_ptr, F) and drops the handshake.
- xlate_ptr behind F: the IFU queues a translation the FTQ then
  presents again, so the IFU translation queue (IFU-25) holds a
  duplicate entry.
- xlate_ptr at or past F: the IFU queues a translation for an index
  at or after F. 4.1 carries no generation tag. If that index is
  squashed and reallocated, a later fetch of the new use can match
  the stale queue entry by index and use the old pc's translation.
What ftq_ifu_interfaces.md 5 requires instead: "A flush and a request
may be presented in the same cycle. The flush applies first: the
request that accompanies it is the first fetch of the corrected
stream." So the request presented in the flush cycle must be the
POST-rewind one: index min(pointer, F). If it is accepted, the
pointer then advances past it. Section 5 flushes both IFU pipelines,
so this is read as covering the 4.1 port too, but the sentence says
only "request". FQ-1 limits what the fetch port could present in
that cycle. After the rewind fetch_ptr <= xlate_ptr <= F, so a
corrected-stream fetch exists only when fetch_ptr was already behind
F, with an entry translated in an earlier cycle. Meeting section 5
needs a same-cycle path: ftq_npc's winning redirect -> ftq_ptr's
min -> the ftq_entry read index -> the ftq_ifu request outputs.
Ports affected.
- IFU boundary, section 4: ftq_ifu_req_val, ftq_ifu_req_rdy,
  ftq_ifu_idx, ftq_ifu_start_pc, ftq_ifu_next_pc, ftq_ifu_taken_val,
  ftq_ifu_taken_pos and ftq_ifu_gen.
- IFU boundary, section 4.1: ftq_ifu_xlate_val, ftq_ifu_xlate_rdy,
  ftq_ifu_xlate_pc and ftq_ifu_xlate_idx.
- Internal: ftq_ptr ifu_req_val/_rdy, xlate_req_val/_rdy,
  fetch_idx, xlate_idx, fetch_pending and xlate_pending; the
  ftq_entry fetch_rd_idx and xlate_rd_idx read ports; the ftq_status
  gen_rd_idx read (ftq.sv:502, 504, 561). ftq_ifu_flush_val and
  _idx are unchanged.
Cost of suppressing val in a flush cycle. The alternative is for
ftq_ifu to drive ftq_ifu_req_val and ftq_ifu_xlate_val low while
redir_val is set.
- Against the as-built design: ZERO slots. ftq_ptr already discards
  the flush-cycle handshake, so suppression only removes the
  duplicate and stale requests the IFU might accept.
- Against section 5 as written: at most one slot per port per
  redirect, and often none.
  - Fetch port: one slot only when fetch_ptr was behind F with a
    translated entry ready. When it was at or past F, FQ-1 leaves no
    fetchable entry in that cycle, so nothing is lost.
  - Translation port: one slot when xlate_ptr was behind F. On a
    p2, p3 or predecode redirect it also costs one slot, because K
    is written and could be translated in the flush cycle, and that
    cycle then carries through to the fetch of K. After a backend
    redirect nothing is lost: with _self clear F is not yet
    allocated, and with _self set F is squashed.
  - The loss per redirect is bounded by one cycle on each port. It
    is small next to the two-cycle p2 redirect cost of 5.6 and the
    extra translation stall of N1.
Suppression also needs section 5 amended to say that no request
accompanies a flush.
