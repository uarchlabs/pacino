# Task Overview

First testbench for bp_cluster. Nothing has ever been driven
through this module.

bp_cluster.sv instantiates all eight predictors, wires p0
through p3, and carries the stage registers, the p1 selection
mux, the RAS branch-type decode, redirect derivation at p2 and
p3, update fan-out by resolved type, the SC credit arbiter and
both prediction-metadata write groups. It elaborates and lints
clean. No prediction request has ever reached it.

This task builds tb_bp_cluster.sv and covers groups A through
F: bring-up, p1 prediction, p2 redirect, p3 and supersession,
history, and metadata. Groups G (a closed predict-then-update
loop) and H (the SC credit arbiter) are separate tasks and are
NOT in scope here.

Group E has a written spec already. BP-092a corrected the
per-slot branch PC reported to bp_history and could not verify
it, because no testbench existed. Its Results Capture records
seven cases, TC-A through TC-G, with exact expected values.
Those are requirements, not suggestions.

## Hypothesis

The cluster boundary plus a small number of hierarchical probes
is sufficient to verify the p1 prediction, the p2 and p3
redirect derivation, the history interface and both metadata
write groups, without a closed update loop and without stubbing
any predictor.

Where the boundary is not sufficient, the gap is nameable in
advance: update fan-out reaching the predictors, the SC arbiter
internals, and the p1 fall-through operand. The first two are
group G and H work. The third was closed by TD#108 -- the
fall-through now leaves the cluster on bpu_pred_pft_p1.

## Background

Every predictor is green in isolation. The cluster is not
simulated at all. lint_bp_cluster is the only target that reads
bp_cluster.sv, so every statement about cluster behaviour in
the planning documents comes from reading RTL and from
elaboration.

Three tasks changed cluster behaviour since it was built and
none of them could be verified:

  BP-091  loop_pred became per-slot. The p1 selection mux lost
          its slot-0 exception, and the p2 loop metadata for
          slots above 0 stopped being zero-driven.
  BP-092  bp_loop_meta_t retired; bpu_meta_lp_p2 retyped. The
          block fall-through was exposed on bpu_pred_pft_p1.
  BP-092a the per-slot branch PC reported to bp_history was
          corrected from a block stride to a real derivation
          from each slot's in-block position.

All three are lint-verified only. This task is where they
become verified.

The metadata write groups added in BP-090 are what make a
closed predict-then-update test possible at all, because the
update inputs embed predict-time metadata. That closed loop is
group G, a later task. This task proves the metadata itself is
correct so group G has a foundation.

### Group A -- bring-up (22 checks, GREEN)

### Group B -- p1 prediction (43 checks)

B1. Selection is per slot with no slot-0 exception. With
loop_pred trusted on slot 1 only, slot 1 reports PRED_LOOP with
the loop direction and br_type COND, and its target and pos
still come from the uBTB entry (target base+0x200, pos 2);
slot 0 reports PRED_UBTB. With loop_pred trusted on slot 0
only, the roles reverse. With confidence one below
LP_CONF_LEVEL the loop entry hits the table but is not trusted
and does not win. This is the BP-091 behaviour that had never
run.

B2. The entry hit and the slot valid are separate terms. A hit
entry carrying no branch in either slot is a legal state: both
slots read invalid, the prediction is still allocated, and the
fall-through still comes from the entry. A miss reports
PRED_NONE with blk hit clear. A hit entry with only slot 1
occupied validates slot 1 alone.

B3. pos propagates from ubtb_pred_t into bp_ftq_slot_t
unchanged, checked at pos 3 and pos 7.

B4. A uBTB RETURN engages the RAS at p1: target 0xABC0 from the
registered top of stack, pred_src PRED_RAS, taken forced. With
an empty RAS the uBTB entry target stands and pred_src stays
PRED_UBTB.

B5. TD#108, never exercised before this task. On a hit
bpu_pred_pft_p1 is blk_p1.pft_addr (base+0x0C) and is
bit-identical to the internal w_pft_p1 the redirect comparison
uses. On a miss from mid-block PC 0x901C it is 0x9000+32, which
also pins the block alignment.

### Group D -- p3 and supersession (50 checks)

D1a. SC override and supersession. TAGE publishes taken at p2
with the branch target as the successor; SC, with its counters
at SC_CTR_MIN, reverses the direction; sc_override is recorded,
the p3 redirect fires, and its target is the fall-through
rather than the branch target. The redirect index is the p3
stage index.

D1b. The complement. With the SC counters at SC_CTR_MAX, SC
agrees with TAGE, the p3 successor equals the p2 successor and
NO redirect fires. A p3 redirect therefore fires only when SC
changes what was published at p2, which is the FE-3 rule.

D1c. With sc_enable low there is no p3 hit and no p3 redirect,
but bpu_meta_val_p3 still asserts, so the entry's slow path is
complete either way (interfaces 7.2).

D2. The BP-093 decision 2 construction, at the boundary, with
no forced metadata and no stubbed predictor. Method: with SC
enabled and an SC update request standing, the cluster's own SC
credit arbiter grants the update on the cycle its prediction
credits run out and drives consumer_ready low for that cycle.
TAGE buffers its result, the cluster p2 stage register advances
anyway, and the next response arrives against a different
index. Over 40 back-to-back requests with incrementing indices
the run observed 28 mismatched responses and 4 matched ones,
and checked the cluster's guard on every one: mismatch rejected
(w_tage_hit_p2 low), match accepted. The queue-status outputs
were read at the boundary throughout and stayed legal.

The construction did NOT prove impossible, so the BP-093 stop
rule for this test was not reached.

Note the second-order finding this test produced. Because of
the C0 defect the 4 "matched" responses are matched by
accident: each carries the branch_id of a DIFFERENT request
than the one it answers. The cluster behaves correctly given
its inputs -- it compares what it is given -- but the guard is
defeated. That is the substance of the defect report.

## Assumptions made not explicit in the prompt

1. NUM_PRED_SLOTS is 2. The testbench indexes generate blocks
   (loop_pred banks, SC tables, ITTAGE tables) by literal, which
   a variable cannot do, and BP-092a's expected values are
   written for two slots. An elaboration-time guard in the
   testbench $fatal(1)s if the package value is not 2, so a
   change cannot silently produce a wrong-shaped run.

2. The three fast-init plusargs (+TAGE_FAST_INIT=1,
   +ITTAGE_FAST_INIT=1, +SC_FAST_INIT=1) are used by
   sim_bp_cluster and cov_bp_cluster. Without them the RAM init
   walk dominates the run and the sanity-time budget is missed.
   The init walk itself is covered by the per-predictor suites,
   which run both with and without the plusarg.

3. "Hierarchical probes are permitted for observation" (BP-093
   decision 3) is read as covering read access to bp_cluster's
   own internal nets, which is where the p1 branch PC, the
   compaction inputs to bp_history and the redirect intermediates
   live. Those signals have no port.

4. BP-092a's TC-A..TC-G name internal signals (w_slot_pc_p1,
   w_hist_pred_pc, w_hist_num_branches, path_bit_0/1). They are
   checked at those names, since the spec is written against
   them; the boundary consequences (pointer advance, PHR and GHR
   contents) are checked at the ports alongside.

5. $isunknown is the X check (A3). Under Verilator's two-state
   value model it cannot report X for a `logic`, so A3 is a
   conformance check that will pass by construction in this
   simulator. It is implemented because BP-093 decision 1 asks
   for it and because it will do real work under a four-state
   simulator; it should not be read as proof that the design is
   X-clean. Stated plainly rather than left implied.

6. A "failing check" for A2 is produced by a plusarg
   (+FORCE_FAIL=1) rather than by editing the file and undoing
   the edit. The exit path exercised is identical and the
   demonstration is repeatable.

7. Repeating an FTQ index on consecutive cycles (req_a) is
   legal stimulus at the port level. Nothing in
   ftq_bpu_interfaces.md forbids it, and the cluster's behaviour
   under it is well defined. It is used only to make the
   TAGE-hit and SC-hit arms reachable while the C0 defect
   stands, and every use is commented as such.

## Decisions made not explicit in the prompt

1. bp_cluster.sv was NOT modified. Constraint 3 permits a change
   only to fix a defect this testbench finds, and the testbench
   found no defect in bp_cluster.

2. The FTB and the RAS are NOT written by hierarchical
   reference, even though decision 3 would permit it. Both
   declare a complete update group at the cluster boundary, so
   every FTB entry in this file is installed through
   ftb_upd_* and every RAS return address through
   ras_commit_*. That keeps the seeded surface smaller and
   exercises two of the update fan-out paths as a side effect.

3. The TAGE T0 bimodal and the five SC counter RAMs are written
   UNIFORMLY -- every row of every bank of both slot RAMs -- so
   the predictor's direction is a constant for any request PC.
   This deliberately avoids encoding either predictor's index
   hash into a cluster test, which decision 3 warns against. A
   table reshape changes the loop bounds only.

4. The ITTAGE entry is the one fixture that cannot be made
   index-free, because a tag must match. Rather than replicate
   ittage_table's hash in the testbench, the index and tag are
   READ from the DUT's own tbl_idx_hash_p0 / tbl_tag_hash_p0
   nets in the cycle the request is presented, and the entry is
   written there. The test then re-requests the same PC with the
   history deliberately held (uBTB miss, so num_branches stays
   0) so the fold feeding the hash is unchanged. No hash is
   assumed.

5. The uBTB and loop_pred index/tag derivations ARE replicated
   in the testbench, because the seeding task needs them before
   the request exists. Every case that uses them calls
   chk_ubtb_hash / chk_lp_hash, which compare the testbench's
   derivation against the module's own p_idx / p_tag /
   req_idx / req_tag in the same cycle. The derivation is
   proven in the run, not assumed.

6. C0 is written as a pinning test with an exact expected value
   (branch_id === the NEXT request's index) rather than as a
   test of the specified behaviour that fails. Rationale: the
   defect is in predictor RTL that constraint 2 puts out of
   scope, and leaving sim_bp_cluster red would block every
   downstream task while telling nobody anything the report does
   not already say. The pinning value is falsifiable: when
   tage_cntrl is corrected, C0 fails and forces this file to be
   revisited. This mirrors tb_ras TC-21, which pins TD#78 the
   same way.

7. do_reset() clears all five ITTAGE tables. They live in
   bw_ram, which has no reset, so rstn alone does not establish
   a known start state for them.

None new. Nothing in this task touches architectural state,
