## Decisions made not explicit in the prompt
All of these are provisional under decision 3. Jeff was not present
(automated run), so the recommended option was taken.
1. csr_tb_pkg additions not listed in CSR-2: csr_reset(), set_priv(p),
   set_v(v) and set_pmp_g(g).
   - priv and V are fe_csr_t members with no address, so they need
     setters like ext_enable.
   - Every testbench needs to establish start state by reset.
   - set_pmp_g exists for tb_pmp_pma_chk's ug0 instance
     (PMP_GRAN_LG2 2): the G 10 read-back would corrupt its G = 0
     NA4/TOR checks.
2. A pmpcfg write of A = NA4 stores NAPOT (at G >= 1). Section 3 says
   NA4 is not selectable but not what a write of it leaves. This
   follows spike, riscv/csrs.cc pmpcfg_csr_t::unlogged_write.
3. csr_write/csr_read to an address with no CSR in csr_pkg stops the
   simulation with $fatal (a testbench error).
4. The shadow is a class with static members and methods behind the
   package functions. This is to keep tb_fe_top's C++ compile time
   bounded; see Problem 4.
5. The PMP checker takes the members it uses (pmpcfg, pmpaddr), typed
   as csr_pkg pmpcfg_ent_t / pmpaddr_imp_t arrays sized PMP_ENTRIES.
   It does not take a whole group:
   - Its two sites are fed from different groups (fe_csr_t,
     ptw_csr_t).
   - Its testbench instantiates it at PMP_ENTRIES 4 and 0.
   - chk_priv stays logic [1:0]: the walker site drives a constant
     PRV_S, so no group can feed it.
   - The ITLB and the walker pass entries [PMP_N-1:0] of their group
     and check PMP_ENTRIES <= CSR_PMP_ENTRIES at elaboration.
6. The ITLB and the walker take their whole group (fe_csr, ptw_csr),
   since each uses every member.
7. The bound property modules itlb_assert and ptw_assert keep their
   ports. Only their bind connections changed, to group members.
   This keeps "no module below fe_top changes its ports" for
   verification modules too.
8. Each of these testbenches drives its group through a tb-local
   variable assigned only from a pack function (fe_cfg, fe_csr,
   ptw_csr), right after the csr_tb_pkg call:
   - The pack result is held in a variable, because a continuous
     assign of a function result is not re-evaluated when package
     state changes.
   - The assignment happens in the same time step as the direct drive
     it replaced.
9. Testbench helper writes of single fields are read-modify-writes of
   the CSR as read.

## RVA23 compliance risks and gaps noticed
These are reported only. Each is a gap in csr_decisions.md, not
changed here.
- henvcfg.PBMTE: [PRIV] makes henvcfg.PBMTE read-only zero when
  menvcfg.PBMTE is 0, as for ADUE. CSR-5 gives the ADUE rule only, so
  csr_tb_pkg does not apply it. tb_fe_top pt_rsv_h
  (W.csr_env(0,0,0,1)) and tb_ptw h_g_pbmte set henvcfg.PBMTE 1 with

  as ADUE did.
- pmpcfg R = 0, W = 1 is reserved in [PRIV]. CSR-5 does not say what a
  write of it leaves (spike clears W). Not applied.
- pmpaddr[i] is also unwritable when entry i+1 is locked TOR [PRIV].
  CSR-5 names only the entry's own lock. Not applied.
- CSR-6 says "The walker samples ptw_csr_t at the start of each
  walk". The walker samples MODE, PPN, ADUE and PBMTE (ptw.sv
  742-754), but its PMP checker reads ptw_csr.pmpcfg/pmpaddr every
  cycle. Kept as it was (no behaviour change); the document text is
  wider than the RTL.
- satp/vsatp MODE Bare with nonzero ASID/PPN is accepted. [PRIV]
  leaves the fields WARL; not an issue for RVA23, noted only.
