## Context Comments

bp_cluster.sv forms the bp_history rollback from its own pipeline
only:

```
  assign w_rollback_valid    = w_any_redir_p2 | w_any_redir_p3;
  assign w_rollback_ckpt_idx = w_any_redir_p3 ? r_idx_p3 : r_idx_p2;
```

THE STATE IS NOT MISSING. bp_history.sv holds ckpt_gptr and
ckpt_pptr, FTQ_DEPTH deep, indexed by FTQ index, written at
allocation from ckpt_wr_en / ckpt_wr_idx, and its rb_apply branch
already restores the pointer pair and recomputes every fold from
ghr_mem. bp_history needs no change at all.

What is missing is the TRIGGER. For a p2 or p3 redirect the cluster
knows the index from its own stage registers. For a backend redirect
the index is known only to the FTQ and no port carries it in.

This blocks ftq_backend_interfaces.md 5 D1. D2, the RAS restore, is
already buildable because ras_restore_val is an input. The asymmetry
is the defect: after a backend mispredict the RAS would be correct
and every history-indexed predictor would index on the squashed
path.

## Hypothesis

The index form is sufficient and the value form buys nothing.

ckpt_gptr[i] inside bp_history and the checkpoint field of FTQ entry
i are written from the same event, the p1 allocation of entry i, and
the array is FTQ_DEPTH deep against an FTQ_IDX_BITS index, so the two
copies are one to one with no aliasing. A redirect names an entry
that is still in flight, so the cluster's copy cannot have been
overwritten by a reallocation of that index. Presenting the index
therefore selects exactly the pair the FTQ would have presented, at
7 bits instead of 14, and with no change to bp_history.

NOTE A DOCUMENT CONFLICT. ftq_decisions.md 3.2 is written for the
value form -- "the FTQ presents the ghist_ptr and phist_ptr from the
checkpoint of the entry being corrected". fe_decisions.md 13 TD-FE-7
and ftq_backend_interfaces.md 8 both specify the index form and
record the choice as open. This task settles it as INDEX and the
wording of ftq_decisions.md 3.2 must follow.

## Background

FE-3 supersession orders the BPU-derived redirects by stage. It does
not decide this one. ftq_backend_interfaces.md 5 states that a
backend redirect outranks every BPU-derived redirect
unconditionally and without comparison, because those are
speculative corrections and this is architectural fact. That is the
whole reason the new input takes priority rather than joining the
existing p3-over-p2 order.

## Binding Previous Decisions

- FE-3 stage-order supersession is unchanged BETWEEN p2 and p3. The
  new input sits above both.
- FE-11: one checkpoint per entry, block granular. No slot
  dimension on either new port.
- The cluster does not read the FTQ. The FTQ presents an index; the
  cluster does not validate it against any queue state.

## Assumptions made not explicit in the prompt

- The FTQ presents the index of the entry whose END-of-block pointer
  state is to be restored, matching what the cluster's own arms do
  with r_idx_p2 / r_idx_p3. Deriving that index from
  bkend_ftq_redir_idx and bkend_ftq_redir_self is the FTQ's job and
  is not modelled here.
- The cluster does not validate ftq_rollback_idx against any queue
  state. It cannot: it does not read the FTQ. An index naming a
  freed or never-allocated entry restores whatever that checkpoint
  slot holds.
- The FTQ does not assert ftq_rollback_val for an entry whose index
  has since been reallocated. The checkpoint array is FTQ_DEPTH deep
  against an FTQ_IDX_BITS index, one to one, so a reallocation would
  have overwritten the value; a redirect names an in-flight entry,
  so this cannot arise.

## Decisions made not explicit in the prompt

- INDEX form, not the pointer values. Settled here, having been left
  open in fe_decisions.md 13. The two copies of the checkpoint are
  written from the same p1 allocation and are one to one, so the
  index selects the same pair at half the wires and leaves
  bp_history untouched.
- The FTQ arm is a flat override, not a new level in the FE-3 stage
  order. FE-3 orders speculative corrections among themselves; an
  architectural correction is not a later stage, it is a different
  kind of thing (ftq_backend_interfaces.md 5).
- Group J was given its own reset helper rather than reusing
  do_reset(), so the group starts from reset plus a known driven
  sequence rather than from whatever G, H and I left in the TAGE
  tagged tables.
- j_alloc builds redirect-free allocations by setting the FTB branch
  target AND the FTB block end AND the uBTB block end all to the
  fall-through. The checkpoint sequence the group depends on is then
  built without any redirect disturbing it mid-construction.

## RVA23 compliance risks and gaps noticed

- None introduced. This is a microarchitectural repair path with no
  architectural visibility of its own.
- Worth stating plainly: without this input, every branch predicted
  after a backend mispredict would have indexed on history from the
  squashed path. That is a performance defect, not a correctness or
  compliance one -- the predictors are hints and the backend
  resolves them -- but it would have been invisible in any test that
  did not measure prediction accuracy across a mispredict.
