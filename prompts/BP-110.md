# Task Overview

TD#124 and TD#125 together. Both are in-block quantities read
against the wrong base, both are in the same files, and TD#125
changes the widths of fields TD#124 rewrites, so splitting them
means editing the same structs twice and rewriting the first task's
tests in the second.

TD#124: pftAddr cannot represent an unaligned block end. The fifth
bit of pft is dead, and at upd_off 64 the reconstruction gives
base+32, wrong by 32 bytes, silently. The uBTB carries the identical
scheme and the identical defect.

TD#125: stored positions are written start-relative and read against
the aligned region base, so every block not starting on a 32-byte
boundary gets a branch PC wrong by the start offset, and a branch an
earlier start recorded is still reported.

Both are green today because the testbenches use aligned bases and
no case crosses two regions. The first problem below is to make them
fail.

Rulings needed
- uBTB slot semantics. With br0 hidden, a visible jump takes slot 0 ahead of br1 at p1. The FTB corrects it at p2, so it's accuracy only, but the uBTB and FTB now mean different things by "slot 0" on the same nominal port shape, and bp_cluster consumes both. Either extend O-3b to the uBTB and fix TC-D, or rule the divergence explicitly in ubtb_interfaces.md.

You can rule either way; I'd apply O-1 to the jump for one rule ("every target is a displacement from its own instruction"), since the 21-bit J-type reach makes the 32-byte cost irrelevant.

- ftb_upd_br_idx_u0. The IA read it as the port slot the update's start saw, which is the only reading under which the FTQ needs no window knowledge — the stated purpose of O-3b. I agree, and the FTQ side is unchanged either way, but it needs ratifying in ftb_interfaces.md rather than living as an assumption in a results file.

## Background
Ruled, all in ftb_decisions.md; confirm each against the document
rather than this paragraph.
- 4.6 R-1: a stored position is REGION-relative,
  FTB_BR_RPOS_BITS = 5. A read keeps only fields whose stored
  position lies in [k, k+16); anything outside reports invalid.
- 4.6 R-2: the conversion is inside the FTB and the uBTB. ftb_cntrl
  adds k at the write from the update PC and subtracts k at the read
  from the lookup PC. Ports stay start-relative.
- 4.6 R-3: a uBTB miss steps to lookup PC + FTB_BLOCK_BYTES, with no
  resync to the region base.
- 4.6 O-1: a conditional target is a displacement from the BRANCH
  PC, which is the region base plus the stored position.
- 4.6 O-2, FTB-G3: a reconstructed end beyond start +
  FTB_BLOCK_BYTES + 2 takes the FTB-G2 fallback, as an end at or
  below the start already does under FTB-G1.
- 4.6 O-3: (a) storage is in ascending region position order,
  (b) the read compacts the window-surviving fields onto the ports
  in ascending position so port slot 0 is the first branch at or
  after the start, (c) 5.4a's fill order is restated on region
  position.
- TD#124: PFTADDR_BITS = $clog2(FTB_BLOCK_BYTES) + 1 = 6 and the
  carry bit is DELETED, in the FTB entry and in ubtb_pred_t.
  Storage is unchanged by this part: 5 + 1 carry becomes 6 + none.
  ubtb_pred_t.carry is also the entry fall-through carry (G18, C9),
  so deleting it leaves that user without a source; read
  ubtb_interfaces.md before assuming otherwise.
- TD#125 costs one bit per stored position, three per entry:
  FTB_ENTRY_WIDTH 110 -> 113 and the RAM entry 109 -> 112. Section 8
  is the sole home of that arithmetic.

## Assumptions made not explicit in the prompt
- ftb_upd_br_idx_u0 names a PORT slot as the update start saw it
  (the compacted view), not a storage field. With O-3b compaction
  the FTQ only ever sees port slots, so this is the only reading
  under which the FTQ needs no window knowledge (the stated purpose
  of O-3b). ftb_cntrl maps the slot back to a field with the same
  window:
  - a slot mapping to a visible field is an in-place update
  - otherwise the branch is a fill into an empty field, else into a
    field hidden from this start
  - storage is then swapped into ascending order
  For an aligned start with no hidden fields this is the identity,
  which is why every existing check is unchanged.
- A jump field whose stored position is outside the update start's
  window belongs to another start, so a jump resolve from this start
  refills it (new position) instead of keeping the old position.
  The same rule applies to a hidden conditional field in the uBTB.

  start (git 7be1da9 plus Jeff's uncommitted changes), not HEAD.
