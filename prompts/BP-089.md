## Background

Three fields the package gained this session are width-checked in
tb_bp_pkg.sv but never driven: bp_ftq_slot_t.pos, the whole of
ftb_pred_meta_t, and the ftb member of bp_ftq_meta_t. The packing
test exists to prove that fields survive a whole-struct copy and
that one slot's write does not disturb another; a field the test
never writes is copied as x and compares equal to x, so it passes
without being exercised.

ubtb blk_p1.pft_addr is the uBTB's block fall-through, reconstructed
from the stored partial value. ubtb_interfaces.md calls it
authoritative for the cluster when no slot is taken. bp_cluster
produces it, registers it, and reads it nowhere.

The place it belongs is the p1 successor operand of the p2 redirect
comparison. That comparison reduces both the p1 view and the p2 view
of a slot to one quantity, the address fetched after that slot, and
raises a redirect when they differ. The p2 view uses the FTB
fall-through for a not-taken slot. The p1 view currently uses the
same FTB fall-through, which is wrong twice over: it is the p2
value, not the p1 value, and using one value on both sides masks the
case the comparison exists to catch, a block whose boundary the FTB
places somewhere the uBTB did not.

blk_p1.pft_addr reads zero on a uBTB miss, so it cannot be
substituted directly. A miss is the common case at start-up, and
zero compared against the FTB fall-through would assert a redirect
on every one. The p1 view of the successor on a uBTB miss is the
next sequential block: the block-aligned start PC plus
FTB_BLOCK_BYTES.

Separately, bp_arb_spec.md 6.1 and TD#91/TD#92 stage the SC
prediction PC and the low ten bits of phr from p0 to p2, because SC
indexes at p2 the block that was requested at p0. The three SC index
folds are connected live to bp_history.folded, which advances
whenever a branch is predicted. Now that the cluster drives
bp_history from a real prediction, those folds move: at p2 they
describe history two requests newer than the block SC is indexing.
The folds are the same class of signal as the PC and the phr and
need the same staging.

Four comment groups in the packages still describe retired
behaviour. The uBTB index and tag comments read PC[26:7], which is
the instruction-granularity indexing the reshape replaced; the uBTB
now indexes at block granularity. ubtb_pred_t.carry is commented as
a property of the slot target; it is the entry fall-through carry.
bp_pred_src_e comments its encodings with s1/s2/s3 stage labels
where the project has moved to p-stage notation. Some of the
branch_id and bp_redirect_t comment corrections of TD-FE-5 may
already be present; verify before editing.

One microarchitectural correctness gap, worth a TD number, found
while confirming blocker 1 rather than by looking for it:

bp_cluster.sv line 923 derives the whole update fan-out
classification from ubtb_upd_u0[gs].br_type. That member no longer
exists. w_upd_type_u0 gates w_upd_cond_u0 and w_upd_ind_u0, which
in turn gate the TAGE, SC, ITTAGE, loop_pred and uBTB update
valids at lines 854, 931, 944, 947 and 950. So the update path of
every predictor in the cluster is currently derived from a
non-existent field. Verilator resolves the read to a 1-bit 1'h0,
per the WIDTHEXPAND warning, which makes w_upd_type_u0 read COND
(3'b000) unconditionally: every update channel would classify as a
conditional branch, ITTAGE would never be updated, and the uBTB
would accept an update for a NO_BRANCH channel. It does not
elaborate, so nothing simulates this today, but the moment the
lint error is repaired by adding the field back rather than by
rederiving the type, the cluster would silently take that
behaviour. The re-scoped task should rederive w_upd_type_u0 from
the structural bits the reshaped ubtb_upd_t does carry -- is_br,
is_jmp, is_call, is_ret, is_jalr -- the same decode ubtb.sv already
implements in jmp_br_type() at ubtb.sv:197-203, rather than
reintroducing a redundant br_type member.

Related, same root cause: w_ubtb_upd_u0 at lines 931-937 forwards
only 6 of the 13 members ubtb_upd_t now carries. is_br, br_idx,
pos, is_jmp, jmp_target, is_call, is_ret, is_jalr and pft_addr are
never assigned, and two of the 6 it does assign do not exist. The
uBTB update port is not correctly driven by the cluster at all.

### Requirement 8: which cases newly redirect

Requirement 8 asks which cases newly redirect. The change was not
made, so this is the intended analysis, not an observed result.

Replacing the p1 operand of the p2 comparison changes the
comparison from

  p1_succ = r_slot_p2[s].taken ? r_slot_p2[s].target
                               : w_ftb_pft_addr_p2

to a p1-view successor staged from p1. Cases that newly redirect:

1. Not-taken at p1 AND not-taken at p2, uBTB hit, and the uBTB
   entry fall-through differs from the FTB fall-through. Today
   both sides read w_ftb_pft_addr_p2 and the comparison is
   identically equal, so no redirect can fire however far apart
   the two views of the block boundary are. This is the case the
   comparison exists to catch and currently cannot see: the FTB
   places the block boundary somewhere the uBTB did not. It arises
   when the two structures hold different block lengths for the
   same start PC, for example after an FTB update that shortened a
   block while the uBTB entry still describes the longer one.

2. Not-taken at p1 AND not-taken at p2, uBTB MISS, where the next
   sequential block, block-aligned start PC plus FTB_BLOCK_BYTES,
   differs from the FTB fall-through. That is any block the FTB
   ends early, i.e. every block containing a taken
   block-terminating branch that the uBTB missed. On a miss the p1
   view is genuinely "next sequential block" and a redirect to the
   FTB fall-through is the correct behaviour.

Cases that do NOT change:
- Taken at p1: the p1 operand is r_slot_p2[s].target in both the
  old and the new expression. Unaffected.
- Any case where the p1 and p2 fall-through views agree, which is
  the steady state once both structures have seen the block.

Note on the miss default, and why it is required rather than
optional. blk_p1 is driven to '0 on a uBTB miss, ubtb.sv line 310,
so blk_p1.pft_addr reads zero. Substituting it directly would
compare zero against the FTB fall-through and assert a redirect on
every miss, which is every block at start-up. The
block-aligned-PC-plus-FTB_BLOCK_BYTES default that requirement 8
specifies is what prevents that. Case 2 above is the residue that
correctly survives the default.
