# Task Overview
Sv57 becomes the mode the translated tests run under (PROJECT_CORE.md
translation modes). This is the last of the three paging-mode tasks:
1. One mode knob for each translating testbench: tb_ptw, tb_itlb and
   tb_fe_top. tools/regress.sh runs them under Sv57, with Sv57x4 at the
   G-stage. A test whose subject is a named mode, or a comparison of
   modes, keeps setting its modes itself.
2. tb_ptw's hand-built Sv39 tests move onto pt_build_pkg, so they can
   run under any mode.
3. tools/regress_weekly.sh runs the same targets under every mode, by
   hand. It gates nothing.
4. A G-stage-only case under Sv57x4 reaches the x4 root's top entries.
5. The trace page-table generator (perf_decisions.md PF-17), built on
   pt_build_pkg, writes a memory image file. The real walker
   translates every page of a generated image.
The shared defaults that examples/fe_demo compiles do not change.

## My Assessment

The only concern with this outcome is the runtime of the regressions. 30 minutes is
too long for an hourly push ci/cd pipeline. 

Suggestions from IA. IA recommends 1 and 2.

  1. Stop rebuilding for every program (about 600 s off every run). Two ways:
     - Take the per-program targets out of REGRESS_TARGETS. sim_fe_top and
       sim_fe_top_1slot already run every program and print each program's count in
       their logs.
     - Or keep them, but have them run the binary that an earlier target in the same
       job built, instead of each depending on the phony build_fe_top.

     Either way fe_top drops to roughly 60-90 s, and bpu becomes the critical path at
     about 300 s. The whole run would then take about 5 minutes instead of 11. This
     undoes BP-121's choice that each program is its own regression target, so it needs
     your ruling.
  2. Run fe_top's 2-slot and 1-slot halves in parallel. They use separate object
     directories. Split them into two Makefiles, or teach regress.sh to run a
     Makefile's _1slot set as a second job. That roughly halves fe_top with or without
     item 1, and it halves the cold-compile hit, since the two cold compiles would run
     at the same time.
  3. Make cold compiles cheaper. This matters on the first run after any testbench
     edit:
     - Move fe_tb_csr.svh's CSR tasks (and the other module tasks the writer calls)
       into classes, as I did in tb_ptw. Each call site then holds one call instead of
       an inlined copy. That took tb_ptw from over 30 minutes to 2 min 15 s.
       fe_tb_csr.svh is shared with examples/fe_demo, so this needs a scoped task.
     - Pass --build-jobs (or -j) to Verilator so the C++ files compile in parallel.
       This only pays once the code is spread across files rather than one giant
       function.
  4. Let scratch copies share the cache. ccache hashes the include paths, so a scratch
     copy of the tree recompiles everything cold; the scratch runs in this task paid
     about 11 minutes per fe_top build. Setting ccache's base_dir to cover the repo and
     the scratchpad would let scratch builds hit the cache. That only affects
     fail-first work, not regress.sh.

  Mechanics for #2:
  - regress.sh runs one job per Makefile and finds Makefiles by path. So the 1-slot
    half needs its own directory, for example rtl/core/frontend/fe_top/slot1/Makefile.
    It would include fe_top's Makefile with SLOT_DEFS set and its own object directory.
  - The two halves already build into separate object directories (obj_fe_top and
    obj_1slot_fe_top), so running them at the same time won't collide. The 1-slot
    sub-make writes only its own object directory, so regress.sh's rule that no target
    writes under another Makefile's directory still holds.
  - They share no ccache entries anyway, because the slot defines change the generated
    C++. So nothing is lost by running them apart.

  some modes is a test of that mode's limit, so it names its mode and
  runs in every run. Examples: the Sv39x4 GPA-bound faults (exp_gpf41,
  t_wide), which no GPA can reach under Sv57x4, run as Sv39x4. A

  under its named mode. A check that cannot be placed this way stops

- EXPECTED VALUES FOLLOW THE MODE. A value that depends on the mode

- TB_PTW ON PT_BUILD_PKG. path3 and gpath3, and the tests built on

  p_pt_gonly and p_pt_vsonly use its mode, and their CSR values come

  - It prints a summary in the form of regress.sh's: one line per

  - It exits non-zero on any failure. It has no waiver list. It runs

  - Its arguments and its job control follow regress.sh's where they

- THE GENERATOR (PF-17):
  - A testbench program on pt_build_pkg: rtl/mmu/ptw/tb/pt_gen.sv,
    built and run by targets in rtl/mmu/ptw/Makefile.
  - Input (+IN=<file>): one hexadecimal virtual address per line. Each
    address names its 4 KiB page. Pages are taken in the order they
    first appear, and a repeated page is ignored. Lines starting # are
    comments.
  - Mapping: the mode is Sv57. Each page gets a 4 KiB leaf with V, R,
    X, A and U set, and W, D and G clear. The physical pages are
    allocated densely in first-touch order from 0x8000_0000 (MMU-15a).
    The table pages come from a pool that starts at the first page
    after the last code page.
  - Output (+OUT=<file>), text, in this order:
