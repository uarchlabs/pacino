# Task Overview
Sv57 becomes the mode the translated tests run under (PROJECT_CORE.md
translation modes). This is the last of the three paging-mode tasks:
1. One mode knob for each translating testbench: tb_ptw, tb_itlb and
   tb_fe_top. tools/regress.sh runs them under Sv57, with Sv57x4 at the
   G-stage. A test whose subject is a named mode, or a comparison of
   modes, keeps setting its modes itself.
2. tb_ptw's hand-built Sv39 tests move onto pt_build_pkg, so they can
   run under any mode.
3. tools/regress_weekly.sh runs the same targets under every mode, by
   hand. It gates nothing.
4. A G-stage-only case under Sv57x4 reaches the x4 root's top entries.
5. The trace page-table generator (perf_decisions.md PF-17), built on
   pt_build_pkg, writes a memory image file. The real walker
   translates every page of a generated image.
The shared defaults that examples/fe_demo compiles do not change.

- THE KNOB. Each of tb_ptw, tb_itlb and tb_fe_top reads one setting,
  the plusarg +PT_MODE=sv39|sv48|sv57. Its default is sv57. Each
  Makefile passes it from a make variable PT_MODE, empty by default,
  to every sim target of that testbench. The G-stage mode is the x4
  mode of the same depth. Every translated test that does not name its
  modes runs under the knob.
- NAMED MODES. A test whose subject is a named mode, or a comparison of
  modes, keeps setting its modes itself, in every run. These are the
  fe_top programs sv39, sv48, sv57 and h57; tb_ptw t_m_a, t_m_b and
  t_m_c; and tb_itlb group P. The IA lists any other test it treats as
  named, with the reason.
- A MODE'S LIMIT IS A NAMED MODE. A test whose stimulus exists only in
  some modes is a test of that mode's limit, so it names its mode and
  runs in every run. Examples: the Sv39x4 GPA-bound faults (exp_gpf41,
  t_wide), which no GPA can reach under Sv57x4, run as Sv39x4. A
  canonical-address fault at Sv39's sign bit runs as Sv39.
- NO SKIP. No test is skipped in any mode. Every check that BP-148's
  run made is made in every run, at every PT_MODE, under the knob or
  under its named mode. A check that cannot be placed this way stops
  the work, and the IA reports it.
- EXPECTED VALUES FOLLOW THE MODE. A value that depends on the mode
  takes it from the mode the test runs under: the levels, the sign
  bit, the GPA bound (SVnnX4_GPA_WIDTH) and the index widths.
- TB_PTW ON PT_BUILD_PKG. path3 and gpath3, and the tests built on
  them, build their tables with pt_build_pkg, in the knob's mode. No
  hand-built path remains. Each test keeps its checks. A test that
  places a bad PTE does so through the builder where the builder can
  place it; otherwise it writes the word directly at the address
  pte_addr gives, and each such site is listed.
- TB_FE_TOP. tb_fe_top's setup takes the knob: reset_all, set_h2,
  p_pt_gonly and p_pt_vsonly use its mode, and their CSR values come
  from the stages the writer builds. tb_fe_top selects the knob's mode
  explicitly.
- THE SHARED DEFAULTS DO NOT CHANGE. models_reset's and the writer's
  own defaults stay Sv39 and Sv39x4, because examples/fe_demo compiles
  them (Background). Nothing under examples/ changes.
- THE X4 ROOT. p_pt_gonly gains a case that names hgatp Sv57x4 and
  fetches code at an address with bits 58:56 set, so the x4 root's
  entries at 0x100 and above are used. It runs in every run.
- REGRESS_WEEKLY.SH, in tools/:
  - Each Makefile with translating targets prints a third
    regress_list line, "weekly: <targets>". regress.sh is not changed.
  - The script runs each weekly target under PT_MODE=sv39, sv48 and
    sv57, in turn, with `make -B -C <dir> <target> PT_MODE=<m>`.
  - It prints a summary in the form of regress.sh's: one line per
    target and mode, and RESULT.
  - It exits non-zero on any failure. It has no waiver list. It runs
    no hook and records no pass.
  - Its arguments and its job control follow regress.sh's where they
    apply (-j, ROOT).
- THE GENERATOR (PF-17):
  - A testbench program on pt_build_pkg: rtl/mmu/ptw/tb/pt_gen.sv,
    built and run by targets in rtl/mmu/ptw/Makefile.
  - Input (+IN=<file>): one hexadecimal virtual address per line. Each
    address names its 4 KiB page. Pages are taken in the order they
    first appear, and a repeated page is ignored. Lines starting # are
    comments.
  - Mapping: the mode is Sv57. Each page gets a 4 KiB leaf with V, R,
    X, A and U set, and W, D and G clear. The physical pages are
    allocated densely in first-touch order from 0x8000_0000 (MMU-15a).
    The table pages come from a pool that starts at the first page
    after the last code page.
  - Output (+OUT=<file>), text, in this order:
    - a header comment that names the generator and the input;
    - `satp <16 hex digits>`: MODE Sv57, ASID 0, and the root's PPN;
    - one `map <va> <pa>` line per page, in first-touch order;
    - one `word <pa> <data>` line per table word, in the order pop
      gives them.
    All values are hexadecimal with no prefix. PERF-002's gasket reads
    this file.
  - An input address that is not canonical under Sv57 stops the
    generator with an error naming the line. So does an input with
    more pages than main memory and the pool can hold.
  - Extracting a page list from a CBP trace is PERF-002's, not this
    task's.
- THE IMAGE CHECK. The real walker reads a generated image: a target
  in rtl/mmu/ptw loads the image of a checked-in sample input into its
  memory model. It sets satp from the image's header, walks every
  mapped page, and checks the PA and the leaf against the image's map
  lines. The sample, rtl/mmu/ptw/tb/pt_gen_sample.txt, is synthetic.
  It covers:
  - addresses in both canonical halves;
  - pages that share each level's table, and pages that need a new
    table at each level;
  - repeated pages;
  - at least 600 distinct pages, so that more than one leaf table is
    filled.
- EXISTING RESULTS. At PT_MODE=sv39, every target gives its BP-148
  result and check count, except where a test was rewritten onto the
