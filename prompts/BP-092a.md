# Task Overview

Fix the per-slot branch PC reported to bp_history.

bp_cluster.sv computes each p1 slot's branch PC as the staged
request PC plus a per-slot FTB_BLOCK_BYTES stride:

  assign w_slot_pc_p1[gs] = r_pc_p1
                          + (VA_WIDTH'(gs)
                             * VA_WIDTH'(FTB_BLOCK_BYTES));

That stride encodes the pre-BP-086 model in which slot 1 was
a lookup of the NEXT block. Since BP-086 one uBTB lookup
returns one entry and both slots describe branches inside the
SAME 32-byte block. Slot 1's branch PC is therefore
overstated by one whole block.

The only consumer is w_hist_pred_pc[], the pred_pc bp_history
folds into the TAGE, ITTAGE and SC index and tag hashes. A
wrong value mistrains those folds on every two-branch block.
It does not affect the prediction the FTQ receives at p1.

Found by BP-092 while correcting the TD#107 comment that had
been describing the retired model. BP-092's constraint 4 put
the expression out of scope, so it was reported and not
fixed. This task fixes it.

bp_cluster has never been simulated. This is a behavioural
fix landing in a module with no testbench, so requirement 6
records the expected values for the future tb_bp_cluster
rather than claiming the fix is verified.

## Hypothesis

Each p1 slot's branch PC is derivable from the block base and
that slot's in-block position, both of which already exist
inside bp_cluster at p1. Replacing the block stride with that
derivation corrects what bp_history is told, changes nothing
the FTQ receives, and leaves every bpu target green.

## Background

Session-063 established the block-descriptor model: one uBTB
lookup returns one entry describing one 32-byte block, and
the two prediction slots are that entry's two conditional
fields. G8 and G17 are superseded. BP-086 removed the
pred_pc_p0 + 32 slot-1 lookup from ubtb.sv.

bp_cluster's w_slot_pc_p1 was written before that and still
strides by a full block per slot. BP-090 gave bp_ftq_slot_t a
pos field carrying the in-block branch position precisely so
the taken branch can be located within the fetch bundle, and
ubtb_pred_t gained pos in the same session. The information
needed for a correct per-slot PC is present at p1.

bp_history consumes this value as pred_pc, compacted by
branch number rather than slot number (session-063), and
folds it into the index and tag hashes of TAGE, ITTAGE and
SC.

### R3. The unit pos counts

UNIT FOUND: expanded-instruction slots of 4 bytes. Not bytes, not
halfwords.

Parameter that fixes it, bp_defines_pkg.sv:
  line 95-96   // In-block instruction position, expanded-
               // instruction granularity
               localparam int FTB_BR_POS_BITS
                                = $clog2(FTB_BLOCK_BYTES / 4);

               UBTB_BLOCK_BYTES.
The "/ 4" in the $clog2 argument is what fixes the unit: the block
is divided into FTB_BLOCK_BYTES/4 addressable positions, so one
position is 4 bytes.

Producer that confirms it: ubtb.sv / the uBTB entry layout. The
entry layout comment at bp_defines_pkg.sv lines 120-121 and 208-209
budgets one pos field per conditional field and one per jump field
inside a single 32-byte block description, and FTB_BLOCK_BYTES is
annotated "32, 8 instr" at line 85. 32 bytes / 8 positions = 4
bytes per position.

SCALING APPLIED: left shift by
  BR_POS_SHIFT = BLK_OFF_BITS - FTB_BR_POS_BITS = 5 - 3 = 2
Declared at bp_cluster.sv line 264. It is DERIVED from the two
parameters, not written as a literal 2, so a change to
FTB_BLOCK_BYTES or to the position granularity rescales it.

Two observations worth recording:

   addresses only 8 positions at 4-byte granularity. Two compressed
   branches inside the same 4-byte expanded slot share a position
   and therefore share a path bit. That is a granularity limit of

   (7 << 2) = 28 to a block-aligned base cannot cross out of the
   block, so no carry into the page number and no canonical-address
   concern.
