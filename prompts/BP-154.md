## Decisions for you, with my recommendations

### 1. R2: an FTB-miss return redirects at p2. I recommend rejecting it.

R2 is not a defect. Without it, the RAS pops correctly at p2 and fetch
follows the stale p1 target until the backend corrects it. No wrong
state is left behind. It is a missed prediction.

The case against it, by the standard you used for RC11:

- **Benefit.** It removes 1 return over the 25 runs. It fires in 2 of
  37 runs. In the one classified run where it fires, web_11 (5, 5):
  - mispred_return goes from 8,245 to 8,240;
  - conditionals rise by 31;
  - cycles go from 2,013,187 to 2,013,572, which is 385 slower.

  The IA traces the conditionals to timing, and I accept that trace. The
  point is that the run gains nothing measurable.
- **Cost.** It adds hardware to p2:
  - a new p2 redirect condition;
  - a mux that selects the p1 view's slots for the slot write;
  - a mux that selects the p1 view's branches for the rollback bundle.

  It also changes what bpu_slot_val_p2 means to the FTQ: the FTQ now
  sees p2 slot writes on an FTB miss, which it never saw before. That is
  an interface change on the p2 path.

### 2. The speculative size: I recommend keeping 16, which is your ruling.

What Phase 2 shows. I recounted every total from the rows. "Wrap-type"
means wrap + fb_uncommitted + bos_rewind, summed over the six traces.

| resolve to commit | wrap-type at 16 | wrap-type at 32 | mispred_return 16 / 32 | cycles 16 vs 32 |
|---|---|---|---|---|
| 50  | 22    | **2** (the IA says 3) | 11,711 / 11,712 | 16 is 3,187 faster |
| 100 | 859   | 9  | 12,554 / 11,719 | 16 is 3,381 slower |
| 200 | 6,860 | 79 | 18,571 / 11,816 | 16 is 11,649 slower (0.146%) |

- At 200 cycles, 16 entries cost 6,755 more return mispredicts, which is
  59% more than at 50 cycles. Even so, cycles differ by only 0.146%. The
  reason is that the FTQ is full for 3,361,993 of the 7,990,755 cycles
  (42.07%), so fetch is already stalled and a return redirect costs
  little.
- The lag in these runs is fixed: every block waits 50, 100 or 200
  cycles. A real machine sees short lags most of the time and long ones
  in bursts, behind cache misses, and in those bursts commit is stalled
  as well. That makes Phase 2 pessimistic for 16 entries, and the cycle
  cost is still under 0.15%.
- The returns that 32 entries do not remove (90) come from the
  allocator rule, not from the size (decision 3).

On cycles, the data supports 16. If you want one more measurement
before closing RAS-2, run a bimodal --resolve-commit distribution
(mostly short, with bursts at 200) at 16 and 32. That is optional.

### 3. The allocator rule (the BOS jump): I recommend a debt entry now and a design task later.

This is the most important finding in BP-154. When a return commits, it
sets BOS to its snapshot TOSR with no generation check. Under a long
lag, that TOSR can name an index the allocator has already reused, or
one ahead of uncommitted calls. Live, uncommitted entries then end up
below BOS, and their returns read the empty stack.

- **It happens at both sizes.** The 32-entry residuals and the 16-entry
  fb_uncommitted case in compress_1 (5, 5), at cycle 665999, are this
  mechanism.
- **Adding entries only makes it rarer.** It does not remove it.

By the letter of your fix rule, the IA should have built a fix, since
ras.sv is in the AREA. It deferred instead and said RAS-2 decides.
Given your concern about scope, I think the deferral was the right
call. I recommend opening it as TD-RAS-BOSJUMP and handling it in a
later design task that measures the fix first. The IA suggested two
directions: protect the indices that live snapshots name, or allocate
from a free list.

THE IN-FLIGHT COUNT (perf/src/harness/ras_class.h, observation only).
rc_max_spec_depth is TOSW - BOS modulo RAS_SPEC_ENTRIES: it reads 15 in
every 16-entry run with any depth and cannot show a lap. rc_max_inflight
is the same distance unwrapped: the speculative allocations (p2 pushes,
p3 missed pushes, C1 and backend pushes) whose FTQ instance no commit has
passed yet (instance number above the last committed one); squashed
blocks' allocations count until a younger commit passes them, as BOS
does. rc_cyc_lap counts the cycles it stood at RAS_SPEC_ENTRIES - 1 or
more. It is an approximation in one direction: a C1 or backend push on an
older instance is counted until it reaches the head of the list
(over-count, never under-count).
