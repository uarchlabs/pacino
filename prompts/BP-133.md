### Problem 2: TD#78, RAS undo-pop over a recursion pop
What ras.sv did: a p2 pop on an entry with rctr != 0 decrements the
count and holds TOSR (st_retract). A p3 undo-pop (q_pop & ~s3_pop)
called st_restore, which restores the registered pre-op TOSR (same
value) and makes no write, so the count stayed decremented: the stack
lost one recursion level. The whole-RETURN_CALL undo
(q_pop & q_push & ~s3_pop & ~s3_push) likewise restored TOSR only.

Reachable: yes. bp_cluster.sv drives ras_pred_val_p3 =
r_val_p3 & r_brv_p3 & w_reach_p3 (the "RAS p3 repair inputs" assign,
BP-121, TD#166). w_reach_p3 uses the SC direction, so when SC reverses
an earlier conditional in the block, a return reachable at p2 becomes
unreachable at p3 and the undo-pop runs. ras_decisions.md section 1
says the same ("The p3 view now differs from p2 when SC reverses a
direction..."). The type stays the registered p2 type, so only plain
undo / missed operations occur (TD#165 analysis unchanged). Established
by reading bp_cluster.sv and confirmed by the probe: at 2 slots
recur shows an undo-pop (one, over a TOSR-moving pop, dec 0) and
misp_call / recur show undo-pushes. No program produced an undo over a
recursion-decrement pop, so the defect is reachable by construction
but not exercised by the current program set.

Provisional fix (decision 3): register per slot what the p2 op did
to the recursion counts and reverse it in the undo.
- ras.sv: new p2->p3 registers p3_pop_dec_q (the pop decremented the
  count at the pre-op TOSR), p3_push_inc_q (the push incremented a
  count, not set when saturated) and p3_inc_ptr_q (where).
- new primitive st_rctr_adj (one write, +1 or -1, no step past 0 or
  RCTR_MAX).
- undo-pop: st_restore, then +1 at the pre-op TOSR if the pop
  decremented.
- whole RETURN_CALL undo: restore TOSR; if only the pop changed a
  count, +1 at the pre-op TOSR; if only the push did, -1 at
  p3_inc_ptr_q; if both, they are the same entry and cancel.
- Write-port budget unchanged (at most two writes per slot per pass).
Undo-push and missed pop already reverse a recursion increment
(st_retract decrements in place); unchanged.

  committed call (commit_arms), so a recursion of depth N is N

  limit is capacity: the commit stack holds 32 calls uncompressed,
  while the speculative stack holds up to 16 entries x 16 levels.
  That is a sizing question, not TD#79.
- No RTL change. New test tb_ras TC-39: commit A then B three
  times, pop with the speculative stack empty: B, B, B, A, empty; and
  c_cnt is 4 after the four calls.

### Problem 4: TD#89 and TD#90
Before and after (no RTL change to the SC update path):

  block, sc_upd_inp_u0[s].branch_range = w_br_pc[s][6 +: 10], with
  w_br_pc[s] = upd[s].pc + (upd_entry[s].slot[s].pos << POS_OFFSET_BITS).
  upd[s].pc is the FTQ entry's block start (ftq_resolve.sv fanout,
  upd[rsv_slot[c]].pc = rsv_entry[c].pc) and slot[s].pos is the
  position of the slot the resolution was mapped to by position match,
  or the new slot when placed (upd_entry[...].slot[...] = w_new_slot).
  Either way it is the resolved branch's own position, so w_br_pc is
  the branch PC at 2 and at 1 slots.
- sc_upd_inp.backwards_branch, per slot s: same block,
  (upd[s].actual_target < w_br_pc[s]). actual_target is the backend's
  resolved target, which for a conditional is the TAKEN target
  whatever the direction (ftb_decisions.md 5.5; tb_fe_top resolve
  task). So the flag is the sign of the branch target, the TD#90
  value, for taken and not-taken resolutions; and sc_cntrl reads it
  only when resolved_taken (global_next, BrIMLI maintenance).
- Path to SC: ftq_upd_conv -> ftq.sv sc_upd_inp_u0 -> fe_top ->
  bp_cluster sc_upd_inp_u0 -> sc.sv update queue -> sc_cntrl,
  unchanged in every hop.
Choice made: no FTB bits stored. Both values are derivable at the
update from the FTQ entry (block PC + slot position) and the
