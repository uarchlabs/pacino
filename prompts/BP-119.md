❯ show me the proposed fix for the unmapped resolution                          

● This is the proposal as it stands in Results Capture (Other Notes). No RTL was
  changed for it.

  The proposal

  An unmapped resolution of a live entry is the first execution of a branch that
  entry does not hold. Today ftq_resolve reports it (rsv_nomap) and forms
  nothing. The proposal is that it trains instead:

  1. Place it in a slot. ftq_resolve picks a slot the same way ftq_ifu W1 places
     a branch predecode found: program order, meaning the lowest free slot, or
     the lowest slot whose position is at or after the branch's.
  2. Form the FTB and uBTB updates from the resolved facts: the type, direction,
     target and position from the resolution, and the fall-through from the
     entry. The FTB's hit and way come from that slot's metadata, so on an FTB
     miss the update allocates. The next prediction of that block then carries
     the branch, and from then on its resolutions map normally.
  3. The open question for the ruling: should TAGE, SC, LP and ITTAGE also train
     on this first execution, using the per-slot metadata captured at predict
     time? This is governed by ftq_entry_formats.md 3.1, rules R1 and R2.

  Alternative

  Predecode writes every control transfer it finds into the entry, not only a
  structural mispredict. Today it inserts only JALs, because a JALR "never M1".

  Why the ruling is needed

  - The table predictors key their metadata to a slot. For a branch the entry
    didn't hold, the slot that metadata belongs to has to be defined, which is
    the choice in step 1.
  - The R2 rule (stored type disagrees with resolved type: train the uBTB and
    FTB only) would decide the default if the ruling chooses not to train the
    table predictors.
  - ftq_entry_formats.md 3.1 currently calls an unmapped resolution "a stale or
    aliased FTB entry". In the integrated front end, the common case is the cold
    first execution.

  Expected effect

  The 8 failing tb_fe_top checks should pass, and loops and coro should start
  predicting correctly after their first iterations. That is untested: no change
  has been built to confirm it.

The main finding: a new branch could never be learned

A conditional branch or JALR that the FTB didn't already hold never got a slot in its FTQ entry. That was true before this task too:

the p2 correction only carries what the FTB returned;
predecode only writes the entry on a mispredict, and that only fires for a JAL.

So when such a branch resolved, it matched no slot, and nothing trained, the FTB included. In the loops program, 88 of 88 resolutions were unmapped, and TAGE, SC, LP and ITTAGE got zero updates in every program. Fixing the converter alone would not have made the predictors learn.

What was built on your ruling: an unmapped resolution of a live entry is placed in a slot in program order, using the same rule predecode corrections use. It then trains every predictor its type calls for, from that slot's saved predict-time state. The entry records the placed slot, so commit sees it.

In loops: 765 → 605 cycles, 79 → 51 mispredicts, and TAGE, SC, LP and ITTAGE all now train.

One thing to record with it: the deferred union layout of ftq_entry_formats.md 3.1 picks which predictor's state a slot holds based on the slot's stored type. A placed branch can land in a slot whose stored type is different. If the union is ever built, placement has to be revisited. Today all the state is stored for every slot, so nothing is wrong now.

A second defect, exposed by training (not fixed)

An FTB entry covers a 32-byte region and has one jump field. When a different jump in the same region trains it, ftb_cntrl.sv keeps the stored position and overwrites only the type and target. The rule says "preserved on an in-place jump-target rewrite", which was meant for the same jump getting a new target.

In the coroutine program, a return-call at position 4 and a return at position 9 share a region. The entry ends up saying "RETURN_CALL at position 9", and all 20 return-calls mispredict. That program got slower, 399 → 550 cycles. ubtb.sv has the same rule, and the conditional fields behave the same way.

Recommendation: fix it. Keep the stored position only when the update's position matches; otherwise rewrite the field. For a conditional field, treat it as a new branch. It costs accuracy only, but this is design intent being violated, like the uBTB jump bug, so it doesn't need to wait for measurement.
