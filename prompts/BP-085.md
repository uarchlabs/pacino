## Background

BP-084 built bp_cluster.sv as instantiation and wiring only. Its
Results Capture lists every tie-off and every undriven output with
the reason each had no producer. That list is the work of this
task.

The prediction pipeline:

```
  p0   request presented; RAM indices driven; RAS top-of-stack read
  p1   uBTB and loop_pred outputs; prediction formed; FTQ allocates
  p2   FTB, TAGE, ITTAGE, RAS
  p3   SC
  u0   update address and write data to the RAMs
  u1   RAM write completes
```

fe_decisions.md is the theory of operation. ftq_bpu_interfaces.md
is the port specification. Both are authority; the RTL port
declarations are authority for port names and widths.

## Binding Previous Decisions

- The cluster stages the PC from p0 to p2 (TD#91) and captures
  phr[9:0] to sc_phr_p2 (TD#92). TAGE does not return the PC:
  tage_pred_meta_t has no pc field. sc.inp_pc_p2 and ras_pc_p2 are
  driven from the cluster's own staged copy.
- Redirect derivation compares a predictor's stage output against
  the prediction the cluster formed at p1 and carried forward in
  its own pipeline registers. bp_cluster does not read the FTQ.
- Predictors declare no redirect ports. The redirect is derived at
  the cluster boundary and driven out on the section 6 ports.
- Redirects supersede by stage order. A p3 redirect wins over a p2
  redirect for the same entry index and slot. Supersession does not
  cross slots (FE-3).
- br_type selects the redirect target source: RAS for a return,
  ITTAGE for an indirect, TAGE then SC direction for a conditional,
  FTB target for a direct unconditional (fe_decisions.md 3.3).
- ras_br_type_p2 is bp_br_type_e decoded from ftb_is_call_p2,
  ftb_is_ret_p2, ftb_is_jalr_p2 and the FTB slot fields.
- Update fan-out by resolved br_type is fe_decisions.md 7.2. The
  three encodings that table does not list follow from what each
  predictor does: NO_BRANCH forms no update; DIRECT_CALL pushes
  RAS and updates uBTB and FTB; INDIRECT_CALL updates ITTAGE for
  the target and RAS for the return address (session-061 ruling).
- Arbitration is bp_arb_spec.md. It lands here (TD#73, TD#94).
- loop_pred is single-slot as declared. TD#105 is the retrofit and
  is NOT in this task. Slot 1 takes the uBTB prediction.
- loop_pred's output port is pred_p0, a known mislabel (TD#105).
  Use the declared name.
- TD#102: bp_history does not generate the IT5 folds. Not in scope.
- BUG-006: build from the tree. If a Context Loaded path does not
  exist, STOP and report it.

## Assumptions made not explicit in the prompt

1. The resolved br_type of update channel s is taken from
   ubtb_upd_u0[s].br_type. It is the only per-slot update payload at
   the cluster boundary that carries a branch type, and uBTB appears
   in every row of the fe_decisions.md 7.2 table, so a valid channel
   always presents one. The field is read independently of
   ubtb_upd_u0[s].valid, so a channel that drives only the table
   predictors still classifies correctly. An all-zero ubtb_upd_u0
   decodes to COND (3'b000), which passes uBTB, FTB, loop_pred, TAGE
   and SC and blocks ITTAGE and RAS -- the safe default for a
   direction-only update.

2. The FTB update channel is classified from its own payload
   (ftb_upd_is_br_u0, ftb_upd_is_jmp_u0), not from a prediction
   slot's br_type. It has no slot dimension, so cross-referencing it
   to a slot would be arbitrary; its own structural flags are the
   direct equivalent of "not NO_BRANCH".

3. INDIRECT_CALL updates uBTB and FTB in addition to ITTAGE and RAS.
   The binding decision names only ITTAGE and RAS for that encoding,
   but uBTB and FTB appear in all four rows the 7.2 table does list,
   and both store a target for any branch type. Excluding them would
   leave an indirect call absent from the two structural predictors.

4. The loop_pred single update channel is update channel 0. TD#105
   is the dual-slot retrofit; until then channel 0 is the only one
   with a producer for it.

5. bp_arb_spec.md rule 1 ("resp_buf_full: no grant") is mapped to
   sc_ready. sc.sv exposes no response-buffer full flag; sc_ready is
   the only SC condition at this boundary that means "the SC cannot
   take a prediction yet". It is low only until RAM init completes.

6. The SC arbiter's prediction request is the cluster p2 stage valid
   (r_val_p2), not tage_pred_rdy_p2. tage.sv already qualifies

## Decisions made not explicit in the prompt

1. The uBTB p1 result is registered inside the cluster. This is the
   producer-alignment decision described under What was delivered. It
   is the one place where the shipped port name and the shipped
   timing disagree: ubtb.pred_p1 is combinational from pred_pc_p0.

2. The FTB jump field is placed in the lowest prediction slot that
   carries no valid conditional field. The jump is the block-
   terminating branch, so lowest-free-slot placement is program
   order and no position comparison against ftb_br0_pos_p2 or
   ftb_br1_pos_p2 is needed. When both conditional fields are valid
   the jump field has no slot; see RVA23 item 2.

3. Every p2 and p3 comparison is qualified by a branch_id match
   against the FTQ index in the matching stage register:
   tage_pred_meta_p2[s].branch_id == r_idx_p2, likewise for ITTAGE at
   p2 and SC at p3. tage, ittage and sc all have queues and can
   return a result later than the fixed stage depth. Without the
   match a delayed response would be compared against a different
   entry's p1 prediction. When the match fails the earlier-stage
   result stands and no redirect is derived. This makes the redirect
   logic self-contained: it assumes no fixed predictor latency.

4. RAS p2 operations are gated by reachability across slots. A taken
   branch in slot 0 ends the block, so slot 1 is off the predicted
   path and must not push or pop. This is FE-11 expressed as logic
   rather than as an assumption. The redirect itself is NOT gated by
   reachability: the FTQ re-derives the successor across slots
   (fe_decisions.md 2.4) and a slot correction is still valid
   information for an entry that a later redirect may re-reach.

5. The p3 redirect compares against the p2-corrected value, not
   against the raw p1 prediction. Comparing against p1 would re-fire
   at p3 every p2 redirect. Supersession is unaffected: FE-3 says
   the later stage wins for the entry index and slot it names, and
   the FTQ applies that rule.

6. The redirect comparison is expressed as one quantity, the slot
   successor address, rather than as a taken/target pair. Both the p1
   and the p2 view are reduced to "the address fetched after this
   slot", using the FTB fall-through for a not-taken slot. Two
   not-taken views therefore compare equal and raise no redirect.

7. The SC arbiter has no update FIFO. bp_arb_spec 4.4 has the
   producer hold valid until accepted and 4.3/4.4 both define a
   bypass path for the empty queue; with the FTQ as the holding
   element a bypass-only queue is the degenerate legal case. This
   also keeps requirement 7 and requirement 8 consistent: the update
   fan-out drives sc_upd_val_u0 directly and the arbiter gates it,
   rather than a queue standing between them. The boundary
   sc_upd_rdy becomes the section 4.4 accept, asserted only on an
   update grant.

8. The prediction request is gated on tage_pq_not_full and
   ittage_pq_not_full and the gated valid drives ftb, loop_pred,
   tage and ittage together. Gating all four keeps the predictors in
   lockstep so the stage registers describe one request across the
   whole cluster. bp_arb_spec 8.1 has fetch stall when any PQ is
   full; the cluster has no request-ready output port, so the
   queue-status outputs at the boundary are that signal and the FTQ
   must observe them. No new port was needed.

9. bp_history pred_taken and pred_pc are compacted. bp_history
   indexes them by branch number, not slot number, so a valid slot 1
   with an invalid slot 0 is reported as branch 0. Its ports are
   literal [1:0] and [2] (INFRA-011 item 10), so at most two branches
   are reported.

10. pred_pc[1] is r_pc_p1 + FTB_BLOCK_BYTES, matching the slot 1
    lookup ubtb.sv actually performs. See RVA23 item 1.

11. bp_ftq_slot_t.confidence is driven to zero. FE-U3 records that
    nothing in either path reads it and that FTQ_CONF_BITS is a
    placeholder. No predictor at p1 produces a confidence in that
    encoding.

## RVA23 compliance risks and gaps noticed

No new RVA23 architectural compliance risk. This task adds control
behavior inside the branch predictor; it introduces no architectural
state and no instruction semantics. Branch prediction is a
performance mechanism and a wrong prediction is corrected by the
redirect and update paths already specified.

Two design conflicts were found. Neither is an RVA23 conformance
issue; both are microarchitectural model conflicts that affect
prediction accuracy and should be dispositioned before tb_bp_cluster
is written.

1. The uBTB slot model contradicts the FTB slot model.

   ubtb.sv gen_pred derives slot 1 from pred_pc_p0 + 32, so its two
   slots are two consecutive 32-byte blocks. fe_decisions.md section
   10 and ftb_decisions.md 2.1/2.3 state the opposite: the two slots
   are the two branch fields of ONE 32-byte block, and section 12
   explicitly retires the two-PC-range model as a TAGE/ITTAGE bundle
   split that does not govern the FTB.

   The consequence lands exactly on this task. The p1 prediction for
   slot 1 describes the block at PC+32; the p2 FTB result for slot 1
   (br1) describes the second branch field of the block at PC. The
   p2 redirect for slot 1 therefore compares two different blocks and
   will fire spuriously whenever both are valid and disagree.

   Slot 0 is unaffected: both models agree that slot 0 is the block
   at PC.

   The cluster was built to the authority documents (interfaces 5.1:
   br0 to slot 0, br1 to slot 1) and the conflict is reported rather
   than resolved here, because resolving it means changing ubtb.sv,
   which the Constraints forbid. Recommend a TD entry against
   ubtb.sv, alongside TD#105.

2. The FTB block has three branch fields and there are two slots.

   ftb.sv presents br0, br1 and jmp for one block. NUM_PRED_SLOTS is
   2. A block containing two conditional branches AND a terminating
   jump cannot be represented: the jump field has no slot and this
   cluster drops it. The dropped case is silent -- no output records
   it.

   The FTB can only be reached at p2, so the effect is a missed p2
   correction, not a wrong architectural result. Recommend a TD entry
   and a decision: either raise NUM_PRED_SLOTS to 3 for the FTB path,
   or have the FTB suppress br1 when a jump is present.

3. Restated from BP-084, unchanged: TD#102, bp_history does not
   generate the ITTAGE IT5 folds. it_t5_idx_fh, it_t5_tag_fh1 and
   it_t5_tag_fh2 reach ittage.folded_hist but read zero. IT5 is the
   longest-history ITTAGE table, so indirect prediction accuracy is
   degraded. A performance gap, not a compliance gap.

4. The 8-wide dispatch target is unaffected. NUM_PRED_SLOTS is 2 and
   every per-slot array is driven across the full slot range, except
   loop_pred which is single-slot by declaration (TD#105).

### bpu_pred_ras_p1

The FTQ entry allocated at p1 needs the RAS pointer state that block
will start from. ras.sv exposes a p0 top-of-stack read and a p2
post-op snapshot; there is no p1 snapshot port.

In the cycle a block is at p1, the block ahead of it is at p2, and
ras_snapshot_p2 of the highest slot is that older block's post-op
pointer state. That is exactly the state the p1 block will start
from when it reaches p2. So bpu_pred_ras_p1 is
w_ras_snapshot_p2[NUM_PRED_SLOTS-1], read in the p1 cycle. One
snapshot per entry is sufficient (FE-11).

The derivation is exact only when no RAS restore lands between the
two cycles. A restore is itself a redirect, and a redirect discards
the entry being allocated, so the stale snapshot is never used.

### Why p2 is split into two always_comb blocks

p2_class_comb drives the RAS p2 inputs. ras.sv produces
ras_pop_addr_p2 combinationally from those inputs. p2_succ_comb reads
ras_pop_addr_p2. If both were one block, that block would write a
signal the ras instance reads and read a signal the ras instance
writes, which is circular at block granularity and produces a
Verilator UNOPTFLAT warning even though no signal-level loop exists.
Splitting resolves it. p2_class_comb reads no ras output.

### Generate block style

One generate region containing exactly one unconditional genvar
for-loop over the prediction slots, named gen_slot. The loop body
holds continuous assigns only: no nested generate, no conditional
generate, no instances, no always blocks. It exists solely to index
the unpacked per-slot port arrays [0:NUM_PRED_SLOTS-1], which a
scalar continuous assign cannot span, and to hold the update fan-out
which must not be an always_comb block (see above). The style is
documented in the bp_cluster.sv file header and matches the existing
gen_pred loop in ubtb.sv.

The genvar is used as a constant select in three places
(w_ftb_br_valid_p2, w_ftb_br_taken_p2, w_ftb_br_target_p2) to give
slot 0 the FTB br0 field and every higher slot the br1 field. The
select resolves at elaboration.
