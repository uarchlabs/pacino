## Context Comments
Writing the FTQ specification exposed three things the BPU and the
packages do not provide. All three are prerequisites for an FTQ that
can be built at all, so they are one task.

1. NO FALL-THROUGH FIELD. fe_decisions.md 2.4 selects the block
   successor as the first taken slot's target, else the block
   fall-through. The fall-through arrives once, at p1, on
   bpu_pred_pft_p1. But 2.4 also says the selection is re-evaluated
   whenever a redirect rewrites a slot, and bp_ftq_entry_t has no
   field to hold the value. The re-derivation as specified cannot be
   performed from the entry.

2. TD-FE-6. bp_ftq_slot_t.br_type and .pos hold the p1 uBTB values
   for the entry's whole life. bp_cluster forms the FTB
   classification in w_br_type_p2 and the positions in
   w_ftb_br0_pos_p2 / w_ftb_br1_pos_p2, uses them internally for the
   RAS and target selection, and carries NONE of them out:
   bp_redirect_t holds target_pc and valid only. Section 7.2 keys
   update fan-out off br_type, so a block the uBTB MISSED and the
   FTB HIT reads NO_BRANCH at resolution and forms NO update at all
   -- the case where training matters most. ftq_bpu_interfaces.md
   7.4 also claims .pos comes from the FTB, which no port made
   possible.

3. NO RESET PC. Nothing in bp_defines_pkg, in planning, or in any
   RTL names one. The FTQ cannot issue its first request.

## Hypothesis
Item 2 cannot be fixed by adding a branch type to bp_redirect_t. A
redirect fires only when the p1 and p2 successors DIFFER, and the
defining case -- a not-taken conditional the uBTB missed -- is one
where they agree, so no redirect fires and the correction never
travels. The classification is needed on every prediction; the
redirect is an exception path. A test built on that case will fail
against a redirect-carried fix and pass against a group valid every
cycle.

## Background
FE-3 supersession, FE-4 cluster-derived redirects and the section 2.4
successor selection were all already specified. None of them was
buildable end to end, for the three reasons above.

## Binding Previous Decisions
- FE-4: the redirect comparison is made at the cluster boundary and
  bp_cluster does not read the FTQ. Unchanged.
- FE-3: supersession is by stage order. The new slot groups follow
  the same rule.
- FE-U3: bp_ftq_slot_t.confidence has no consumer; drive zero.
- TD-FE-4: pred_src is diagnostic. Populate it where the
  information is already to hand, do not add logic for it.

## Specific Requirements
1. bp_ftq_entry_t gains pft_addr, VA_WIDTH, block scalar.
2. bp_cluster gains a slot correction group at p2 and again at p3,
   carrying bp_ftq_slot_t per slot, VALID ON EVERY PREDICTION the
   FTB answers, not only when a redirect fires.
3. bp_defines_pkg gains RESET_VECTOR. It must be FTB_BLOCK_BYTES
   aligned; an unaligned value makes the first fetch a partial block
   and both the FTB and uBTB index on the block-aligned PC.
4. Width checks for every new field, and a test that fails if the
   slot group is gated on a redirect.
5. All 47 bpu targets green. Report every count that moves.

## Constraints
- No predictor module is modified. The gaps are at the cluster
  boundary and in the packages.
- RESET_VECTOR must change no behaviour: nothing consumes it until
  the FTQ exists.
- No known or waived failures.

## Deliverables
- The three additions, their checks, and mutation evidence that the
  new checks can fail.
- Planning documents updated.
- All 47 targets run, counts compared against the prior run.

## What was delivered

1. bp_ftq_entry_t.pft_addr, VA_WIDTH, block scalar, placed after pc.
   Stored rather than re-derived because the p1 port carrying it is
   present only in the p1 cycle while fe_decisions.md 2.4
   re-evaluates the selection on every redirect. Entry 182 -> 222
   bits. (BP-099 later widened it again to 224.)

2. The p2 and p3 slot correction groups on bp_cluster:

```
     bpu_slot_val_p2  bpu_slot_idx_p2  bpu_slot_p2 [0:SLOTS-1]
     bpu_slot_val_p3  bpu_slot_idx_p3  bpu_slot_p3 [0:SLOTS-1]
```

   Mostly wiring: every field already existed as an internal net --
   w_br_val_p2, w_br_type_p2, w_taken_p2, w_tkn_tgt_p2, and the FTB
   positions, which were connected to the FTB instance and read
   nowhere. New logic is the per-slot position select (a jump slot
   takes ftb_jmp_pos_p2, not a conditional position), pred_src in
   the existing target-source case arm, and a p3 stage register
   carrying the slot with the SC direction applied.

3. bp_defines_pkg::RESET_VECTOR = 40'h00_8000_0000. The privileged
   spec leaves the reset PC implementation defined; this is the
   RISC-V convention and the Spike boot ROM target, and the tree
   carries no memory map of its own. Block aligned, verified by
   elaboration probe.

## Assumptions made not explicit in the prompt

- I1 was written to be independent of TAGE state. do_reset() clears
  the ITTAGE tables but NOT the TAGE tagged tables, so a test placed
  after groups G and H inherits their allocations. Rather than seed
  around it the FTB branch target is set EQUAL to the fall-through,
  so the p2 successor is that one address whichever direction wins
  and the case does not depend on TAGE at all. Recorded in a comment
  at the test.
- pred_src is populated from the arm that selects the target, where
  the information is already to hand. No logic was added for it.

## Decisions made not explicit in the prompt

- The correction is a GROUP carrying bp_ftq_slot_t, not a field on
  bp_redirect_t. bp_redirect_t keeps its own job, resteering fetch;
  the new group answers a different question, what the entry should
  record. Conflating them is the root of TD-FE-6.
- The group is published on every prediction the FTB answers rather
  than on redirect. See the Hypothesis.
- p3 changes only taken, and pred_src when SC actually moved the
  direction. SC corrects direction, not branch type, so br_type, pos
  and target pass through the p2 -> p3 register unchanged.
