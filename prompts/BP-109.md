# Task Overview

TD#122. VA_WIDTH is 40 and cannot hold a fetch PC. Change it to 41,
add the nine ITLB/MMU widths no package declares, and remove the
hardcoded address literals that make the width change unsafe.

The literals are the reason this is one task and not two. A 40-bit
literal assigned to a 41-bit field is caught by lint. A `[39:0]`
slice of a 41-bit signal, a `{24{addr[38]}}` sign extension, and a
testbench constant declared `39'h...` are all legal at any width
and warn about nothing. They must be found by search, not by the
compiler, and they must be corrected in the same edit that changes
the width or the tree is wrong while it builds clean.

## My Assessment

I asked the IA to write the proposal for the upper-half kernel performance
issue. The growth is 12Kbits, this is significant enough to want a
performance review before implementation. 

The proposal will be posted to the PA for creation of a TD and for review
in case I have missed a side effect. The file will be misc/prop1.md

From IA:
Recommendation: take the missing high bits from the branch's own PC instead of
  zero-filling them.

  it_tgt = { r_pc_p2[VA_WIDTH-1 : IT_MAX_TGT_WIDTH+1],   // bits 40:39 from the
  PC
             stored_tgt,                                  // bits 38:1 from
  ITTAGE
             1'b0 };

  Why it works
  - Indirect jumps don't cross the half. Kernel code jumps to kernel code and
    user code to user code. Moving between them goes through traps and
    ecall/sret, which are not predicted indirect branches. So bits 40:39 of the
    target almost always equal bits 40:39 of the jump's PC.
  - It covers both modes. A V=0 kernel PC has its top bits set, so the target
    gets them too. A V=1 guest address has whatever the PC has there, and that
    is right unless a jump crosses a 512 GB region, which is rare.
  - It sidesteps the open question. It gives the right answer however a V=0 Sv39
    address ends up stored in the 41-bit PC, so the design doesn't have to
    settle that first.
  - It costs almost nothing. It is a 2-bit splice from a register already in the
    p2 stage: no storage and no timing cost. The FTB already rebuilds targets
    relative to the block base, so this matches how it works.

  Why the other options are worse
  - Widen IT_MAX_TGT_WIDTH to 40 or 41: this costs about 4 Kbit more storage
    across the ITTAGE tables and reverses the session-070 pin. It also buys less
    than the PC splice.
  - Sign-extend when V=0, zero-extend when V=1: the predictor would need to know
    the privilege and translation mode at predict time. That state changes on
    every trap and needs a ruling on how V=0 addresses are stored.

  Why it's worth doing: with zero extension the problem is worse than one
  mispredict per branch. When a kernel indirect jump mispredicts, the update
  writes back the same bits 38:1. The entry keeps its confidence and keeps
  predicting the wrong upper half, so ITTAGE effectively stops predicting kernel
  indirect jumps. The FTB target doesn't take over, because ITTAGE hits and
  overrides it.

  An optional addition: when a resolved target's bits 40:39 differ from its
  PC's, the FTQ could stop ITTAGE from allocating or writing that entry, because
  it can't represent the target. The FTQ has the full PC and target at resolve,
  so this is one comparison, and the FTB fallback would then handle the rare
  cross-region jump.

  This needs a ruling first. Section 5.2 of ftq_bpu_interfaces.md currently says
  "zero extended", and I built exactly that, so I haven't changed the RTL. If
  you want it, the PA would amend 5.2 and a follow-on task would make the change
  in bp_cluster.sv (p2_succ_comb). C1f2 still passes under this scheme because
  its PC has bits 40:39 = 00, so that task should add a check with an upper-half
  PC and target.

[This is significant]
  One correction to my last answer: I said widening the field costs about 4
  Kbit. The real figure is about 12 Kbit, because the field grows by 3 bits (38
  to 41) and each ITTAGE table keeps a separate RAM per prediction slot. The
  proposal uses the corrected number.

## Claude.ai Assessment

Read the whole file. This one is good work, and the evidence is the strongest of the three tasks so far.

What stands out

The grep alone would not have been enough, and the IA noticed. Seven sites got their width from how the expression was built rather than from any number, so no text search could find them — including the ITTAGE reconstruction itself. The IA found them by running the tree at VA_WIDTH 41 on a copy and reading the width warnings. That is the right instinct, and it confirms the division we expected: lint catches the implicit sites, search catches the literal ones, and neither alone is sufficient.

Three-way injection. injA (full pre-fix tree), injB (only the sign extension restored), injC (only VA_WIDTH back to 40). Each new check fails on exactly the defect it targets and nothing else. That is better than the task asked for — it proves the checks are specific, not just sensitive.

One incidental finding worth recording. The testbench model at tb_bp_cluster.sv 3327 was zero-extending ({1'b0, tgt, 1'b0}) while the RTL was sign-extending. The model and the DUT disagreed, and 1795 checks never noticed, because no test ever set bit 38. That is the same blindness TD#122 describes, sitting inside the testbench that was supposed to catch it.

The proposal

The arithmetic works: 2 bits from the PC, 38 stored, 1 zero, 41 total. The reasoning about indirect jumps not crossing the half is sound, and the corrected 12 Kbit figure makes the widen-the-field option clearly worse. Four things to weigh before it becomes a task:

Take the allocation guard with it, not as an option. The proposal's own argument against zero extension is that a wrong entry is sticky: the update writes back the same bits, confidence holds, and ITTAGE keeps overriding the FTB with a wrong target forever. The PC splice has the identical failure for a genuine cross-region jump, just rarely. The guard — the FTQ refuses allocation when the resolved target's bits 40:39 differ from its PC's — is what makes the failure fall back to the FTB instead of sticking. Without it the proposal fixes the common case and leaves the pathology.
Name which PC. r_pc_p2 is the lookup PC, the block base, not the branch's own PC. They differ only if a 32-byte block straddles a 512 GB boundary, which can't happen, but the amendment to 5.2 should say the block base explicitly rather than "the branch's PC", or the two readings will drift apart later.
It does not sidestep the open question as cleanly as it claims. It gives the right answer for reconstruction without knowing how a V=0 address is stored. But the representation question still has to be answered for the IFU, and it reaches further than prediction quality — see below.
The comment the IA just wrote in bp_structs_pkg.sv 283, that the target is zero-extended on use, would need changing again. Minor, but it is now a second site stating the reconstruction.
The thing I'd raise separately

The V=0 representation question is not only a performance matter. A canonical Sv39 kernel address has bits 63:38 all set. TD#122 currently records that a backend-computed JALR target with bits 63:41 set must fault, which is the Sv39x4 GPA rule and is correct under V=1. Under V=0 that same pattern is a legal kernel address. So FE-19, FE-U11 and whatever the 41-bit PC holds for V=0 have to be settled together, and the answer decides both the ITTAGE behaviour and what the redirect PC check rejects. That belongs as an open item against fe_decisions.md, not inside a performance TD.

What I'd do with it

TD#132 for the ITTAGE upper-half targets, carrying the proposal, the guard and the 12 Kbit figure, gated on a ruling to 5.2. A separate open item, FE-U12, for the V=0 fetch PC representation and its effect on FE-19 and FE-U11. TD#122's RTL half is done and can be closed against BP-109, with FE-U11 left open where it already is.

Say the word and I'll write the PROJECT_STATUS changes, the three planning document updates the IA listed in Deferred Work, and new check_planning checksums. I'd like to see misc/prop1.md before drafting the TD, so the TD quotes the proposal you actually have rather than my reading of the console output.

## RVA23 compliance risks and gaps noticed
- A V=0 upper-half Sv39 indirect target loses its high bits in
  ITTAGE.
  - 5.2's zero-extension is right for V=1 GPAs. For V=0, a kernel
    target has VA bits 63:38 all set. Assuming the 41-bit PC holds VA
    bits 40:0 of a canonical Sv39 address, zero extension gives bits
    40:39 = 00, so every upper-half indirect target predicted by
    ITTAGE mispredicts.
  - This is performance, not correctness: resolve redirects, which
    FE-19 allows. It is not ruled.
  - Nothing in Context Loaded says how a V=0 Sv39 VA is held in the
    41-bit fetch PC (truncated canonical form or otherwise). That
    representation decides whether this happens. Recorded, not acted
    on.
- FTB_TAG_BITS 26 leaves PC bit 40 untagged, so two blocks that differ
  only in bit 40 alias in the FTB. This is ruled and accepted (FE-19).
  C1f3 relies on the alias being harmless when there is one PC.
- MMU-U9 (PTE PPN above PPN_WIDTH is unchecked) is noted as out of
  scope, per the task.
