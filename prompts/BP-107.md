## Background

The FTQ decouples prediction from fetch. bp_cluster predicts a block
per cycle and the FTQ holds the results in a 64-entry queue until the
IFU fetches them and the backend retires them. It owns the next-PC
register, so the front end's steady-state loop closes through this
unit and not through the predictors.

Storage is split by access rate. The fast path, bp_ftq_entry_t, is
read every cycle: 224 bits per entry. The slow path, bp_ftq_meta_t,
is read once at resolution: 421 bits per slot, two slots per entry.
Three status vectors -- wb_rcvd, fault, gen -- are flops outside both
arrays because they are written by range rather than by index.

Four boundaries. bp_cluster supplies predictions and takes updates.
The IFU takes fetch requests and returns predecode. The backend
resolves, redirects and commits. The ICache is encapsulated behind
the IFU and has no FTQ interface by decision.

## How the p1 successor was confirmed combinational

Binding Decision 3 asks for the confirmation, not the claim. Three
independent ones:

1. tb_ftq_npc group B drives the p1 group and reads ftq_pred_pc_p0
   WITH NO INTERVENING CLOCK EDGE -- one time unit, against a clock
   period of ten, with the previous edge one unit behind. A registered
   implementation still shows the previous PC at that moment. B1 and
   B2 first establish that the value present BEFORE the p1 group
   arrives is the reset vector and is NOT the expected successor, so
   B3 cannot pass by coincidence.

2. Property N4 states the same fact as a SAME-CYCLE SVA implication
   over all three arms of the 2.4 selection, and runs on every cycle
   of tb_ftq_npc and of the unit testbench. Injecting a registered
   path -- w_sel_pc = r_next_pc on arm 5 -- fires it.

3. tb_ftq group B closes the loop through the whole unit against a
   modelled cluster and counts eighteen consecutive cycles of one
   block each, the PC an arithmetic progression in FTB_BLOCK_BYTES
   with no value repeated. A registered path halves that rate, which
   the progression detects; it does not merely slow the test down.

## Fault injection

EVERY BOUND PROPERTY WAS PROVEN LIVE. 73 properties, 73 faults, on a
scratchpad copy outside the tree; each fault breaks the thing that
property guards, the module's own simulation is rebuilt and run, and
the property's own $error text is confirmed present. The tree is
restored between every case and the driver ends by restoring it.

Two mechanics were needed and both are worth recording:

- VERILATOR STOPS AT THE FIRST ASSERTION FAILURE, so an earlier
  property masks a later one. The runs pass
  +verilator+error+limit+100000 so every firing is recorded.
- A CONCURRENT PROPERTY ONLY SEES STATE PRESENT AT A CLOCK EDGE.
  46 of 73 did not fire on the first pass, and most of those were
  testbenches driving inputs, checking at a delta delay and moving
  on. See Decisions.

## Assumptions made not explicit in the prompt

A1 THE p2 AND p3 GROUPS ARE CHECKED AGAINST THEIR OWN INDICES.
   ftq_bpu_interfaces.md says the slot, redirect and metadata groups
   of one stage all name one entry. ftq_shadow compares each group's
   own index against the stage rather than trusting a shared one. It
   costs a comparator and catches a cluster that ever presented two
   p2 groups for different entries, which nothing else would.

A2 A RESOLUTION FOR AN ENTRY OUTSIDE THE LIVE WINDOW IS THE WHOLE OF
   R3 THAT CAN BE BUILT. See the Deferred Work note on the missing
   generation bit.

A3 THE SAME-INDEX WRITE ORDER IN ftq_entry IS pd > p3 > p2 > alloc ON
   THE SLOT ARRAY, with allocation always writing the block-scalar
   fields. FE-3 gives p3 over p2 and ftq_ifu_interfaces.md 7 puts
   predecode after both; the allocation case is an input error the
   shadow and the generation bit already prevent, and allocation --
   the newest event for the index -- wins it.

A4 ftq_meta HAS NO RESET. The array is read only at resolution and a
   resolution can only name an entry a prediction wrote, so no path
   reads an unwritten location. Clearing 53,888 bits at reset would
   model a structure no SRAM provides. ftq_entry resets only the 64
   valid bits, for the same reason.

A5 THE FETCH REQUEST IS QUALIFIED BY fetch_pending ALONE, with no
   entry-valid term. fetch_pending now measures to the written
   frontier, so the valid bit would be redundant with it.

A6 ftq_ifu AND ftq_resolve CARRY clk AND rstn although both are
   combinational. CLAUDE.md's rule is "only as needed"; a concurrent
   property needs a clock and a disable, and TD#109 requires the bind
   to read the port list.

A7 THE CLUSTER MODEL IN tb_ftq IS ONE p1 RESPONSE PER ACCEPTED p0
   REQUEST, one cycle later, carrying the index it was given, and
   nothing else. That is what ftq_bpu_interfaces.md 3 and 4 promise;
   the model is not a predictor.

## Decisions made not explicit in the prompt

D1 SEVEN PORTS THAT 7.3 DOES NOT ANTICIPATE. Each is reported rather
   than quietly added, as the Hypothesis asks. None breaks the
   partition rule: every one is a value one module owns and another
   reads, and no module reaches into another's advance decision.

   1. ftq_shadow.alloc_inflight -> ftq_ptr. The p0-to-p1 allocation
      gap. 5.1 gives the run-ahead as the gap between fetch_ptr and
      alloc_ptr, but alloc_ptr advances at p0 (5.2) and the entry
      content is written at p1, so for one cycle the newest entry in
      that gap has an index and no content. A fetch issued on the raw
      gap presents an unwritten pc to the IFU, and it is reachable in
      the first two cycles out of reset, not in a corner. The shadow
      already knows -- its p1 stage IS that request -- so ftq_ptr
      subtracts it. THIS IS A DEFECT IN 5.1's STATEMENT OF THE
      RUN-AHEAD, not only a missing port.

   2. ftq_npc.pred_pc_p1 -> ftq_entry. The block start PC.
      bp_ftq_entry_t.pc is the fetch block start and the entry is
      written at p1, but NO p1 PORT CARRIES IT: the group of
      ftq_bpu_interfaces.md 4 has the slots, the RAS snapshot and the
      fall-through. It exists only as the ftq_pred_pc_p0 the FTQ
      issued a cycle earlier, so the FTQ must stage its own request.
      r_next_pc already is that value one cycle on, so publishing it
      costs no state. The alternatives are worse: a PC register in
      ftq_entry is not its state, and widening the shadow by VA_WIDTH
      per stage carries something only one stage needs.

   3. ftq_ptr.squash_val / _start / _end -> ftq_status, ftq_shadow.
      7.3 publishes the winning REDIRECT to ftq_status and leaves the
      masked clear to it. Built that way, ftq_status repeats the
      wrap-generation reconstruction ftq_ptr already performs on
      redir_idx -- two copies of one derivation, free to disagree --
      and ftq_shadow needs a third. The resolved range is exported
      from its owner instead, half open and FTQ_PTR_BITS wide so both
      consumers take an age and neither reconstructs anything.

   4. ftq_entry.ras_commit_* . 5.4 says the commit payload reads
      bp_ras_snapshot_t out of the entry and ftq_commit.sv already
      says the has-a-RAS-operation qualification belongs where the
      fact lives. The payload is therefore formed in ftq_entry from
      commit_step_val and the entry at commit_step_idx.

   5. ftq_entry.rsv_rd_idx / _entry and ftq_meta.rd_idx / rd_meta,
      TWO OF EACH. ftq_backend_interfaces.md 4 fixes resolution at
      NUM_RESOLVE_PORTS per cycle and the two channels may name
      DIFFERENT entries, so one read port cannot serve both.

   6. ftq_entry.pdwb_rd_idx / _entry. ftq_ifu_interfaces.md 7 W1 and
      W3 need the entry the writeback names, in the same cycle, to
      form the slot correction and re-derive the successor. It cannot
      share the redirect read port: that one is addressed by the
      rollback index, which is the arbitration's OUTPUT, and the
      predecode redirect is one of its inputs.

   7. ftq_entry.restore_snapshot. D2 of ftq_backend_interfaces.md 5,
      published as its own port so ftq.sv wires name to name and
      stays free of field selects.

D2 ftq_shadow IS FOUR STAGES AND THREE FLOPS. 5.6 sizes it four deep,
   one per cluster stage p0 through p3, and it was built that way
   first -- with four REGISTERS. That is wrong and it is not subtle:
   the p1 response for a request issued at T arrives at T+1, when a
   four-register shadow holds that request at stage 0, so every
   response is checked against the stage behind it, every response is
   dropped and the front end stops after one block. The p0 stage is
   the request being PRESENTED and is not registered anywhere -- not
   in the cluster either. Four stages, three flops. Found only by the
   unit testbench; no leaf test can see it. 5.6 should say so.

D3 THE SHADOW CARRIES A FULL POINTER, 4 x 8 bits, not 5.6's 4 x 7.
   Deciding WHICH STAGES a redirect clears is a wrap-aware age
   comparison and an index cannot make it. Clearing every stage
   instead is wrong: stage 3 holds an OLDER request than stage 2, so
   a p2 redirect naming the stage 2 entry squashes stages 1 and 0 and
   must leave stage 3 alone. This is NOT the widening 5.6 rejects --
   that was FTQ_IDX_BITS at every bp_cluster port and in four
   metadata structs; this is four bits inside the FTQ.

D4 THE PREDECODE SLOT PLACEMENT RULE. Section 7 W1 says "the named
   slot" and nothing says how a position names one when no slot holds
   it -- the M1 case, where the block was predicted to have no taken
   branch and predecode found an unconditional. Built as PROGRAM
   ORDER, which is what FE-10 and IC-FTB-16 already make the slot
   array: the lowest slot that is invalid or whose pos is at or after
   mis_pos, with every slot above it killed. The kill is not optional
   -- a predecode-found branch at mis_pos is taken, so everything
   after it is off the path.

D5 4.1's r_next_val IS NOT CARRIED AS STATE. It is constant true after
   reset: arm 0 loads the register with the reset vector and every arm
   replaces it with another real address, so no event clears it. 4.5's
   "r_next_val deasserts" is the OUTPUT valid, which the hold gates. A
   flop that could never be zero is dead state.

D6 THE FTB CHANNEL IS PRESENTED WITHOUT REGARD TO THE SCHEDULER'S
   READY. ftq_ftb_sched's upd_rdy is a FUNCTION of the valids
   presented to it (5.7.3 S6), so gating ftb_upd_val on it would close
   a combinational loop through the scheduler. The queued predictors,
   whose readies come from their own queues, ARE gated. Property R15
   states the rule on the fan-out for this reason; it was written
   against the FTB channel first and was wrong.

D7 TESTBENCH STRUCTURE: ONE PER MODULE, PLUS A UNIT TESTBENCH.
   BP-106 used one testbench per module with the neighbour modelled
   as a driven input. That choice is MORE right at eleven modules,
   not less: every acceptance criterion in Problems 2 to 6 is a corner
   -- 64 live entries, a range clear across a wrap, a p2 redirect that
   spares the older p3 stage, ten ordered arm pairs -- and no
   unit-level stimulus can place those. But the leaf tests cannot see
   the loop or the wiring, and D2 above is the proof: an off-by-one
   that dropped every cluster response passed every leaf test. So
   both: eight leaf testbenches for the criteria, and tb_ftq for the
   zero-bubble loop, the redirect fan-out and the wiring.

D8 CONCURRENT SVA IS INERT UNLESS THE STIMULUS CROSSES A CLOCK EDGE,
   and four of this task's testbenches got that wrong. A property
   samples at posedge clk; a case that drives its inputs, checks at a
   delta delay and moves on never presents that state at an edge. Of
   73 properties, 46 did not fire on the first injection pass and most
   of the misses were this. Fixed by a settle() task that holds each
   case's stimulus across an edge. GROUP B OF tb_ftq_npc DELIBERATELY
   DOES NOT USE IT: its checks must read the output with no
   intervening edge, which is what makes them a proof that the
   successor path is combinational. Arm 5 is still sampled -- group C
   presents it in every pair.

D9 $past OVER A FLOP'S OWN COMBINATIONAL CONE IS NOT RELIABLE, and
   two properties reported a mismatch the design does not have.
   ftq_npc N8 compared pred_pc_p1 against $past(ftq_pred_pc_p0) --
   pred_pc_p1 IS r_next_pc, and ftq_pred_pc_p0 is w_sel_pc whose hold
   arm reads r_next_pc, so the two sit in one cone around the flop.
   ftq_shadow H4 had the same shape once stage 0 became
   combinational. Both restated against a registered copy held in the
   assertion module, which is the form ftq_status_assert already
   used and which is an independent model rather than a
   reformulation of the DUT.

```
  NUM_RESOLVE_PORTS = NUM_PRED_SLOTS                      // = 2
```

  third resolution in one cycle could not be forwarded. Derived from
  NUM_PRED_SLOTS rather than written as 2, so the two cannot drift.

```
  FTQ_PD_POS_BITS = $clog2(FTQ_PD_WIDTH)                  // = 4
```

  The names the task Constraints specify, with the derivations

  dependency puts them. They coincide with 2**FTB_BR_POS_BITS at the
  shipped geometry and the comment records that the two are separate
  derivations, so a change to either must be checked against the

## RVA23 compliance risks and gaps noticed

R1 NONE INTRODUCED. The C extension is what makes FTB_BR_POS_BITS 4
   and FTQ_PD_WIDTH 16, and both are honoured: the predecode-to-
   predictor position conversion is the identity, and ftq_ifu guards
   it with an explicit width-equality test rather than a shift, so if
   the two ever diverge again the conversion drives zero instead of
   silently truncating. tb_ftq_ifu refuses to run if they differ.

R2 IN-BLOCK POSITION IS pos << POS_OFFSET_BITS THROUGHOUT, and no
   literal 2 or 4 appears anywhere in the delivered RTL. In practice
   the FTQ does not scale a position at all -- it stores, compares and
   forwards positions and never converts one to a byte offset -- so
   the parameter is used by not being needed. The one place a byte
   quantity appears is the testbench cluster model, which adds
   FTB_BLOCK_BYTES, not 32.

R3 THE RETURN ADDRESS OF A CALL IS THE ONE RVA23 GAP WORTH NAMING.
   Under the C extension a call is 2 or 4 bytes and the FTQ entry
   records neither the length nor the address after the call. See
   Deferred Work, item 1.

## Deferred Work

W1 ras_commit_ret_addr IS WRONG ON A uBTB MISS, and the fix is a
   PLANNING CHANGE outside this unit. CHECKED against
   ras_decisions.md after the run, on Jeff's instruction; the file is
   not in the Context Loaded manifest.

   ras_decisions.md 8 names the source outright: ret_addr is
   call_pc + 2 or + 4, and "the FTB fallThroughAddr field provides
   this value". The RAS consumes it and explicitly does NOT compute
   PC+2 or PC+4 itself, so the FTQ's job is to forward the right
   field, not to derive one. Section 3.3 states the push; section 8
   states the value.

   THE FTQ DOES NOT HAVE THAT FIELD. bp_ftq_entry_t.pft_addr is
   written once, at p1, from bpu_pred_pft_p1, and
   ftq_bpu_interfaces.md 4 says of it in as many words: "It is not
   the FTB pftAddr of section 5.1, which arrives at p2." The FTB's
   ftb_pft_addr_p2 is consumed inside the cluster and no port carries
   it out; the p2 and p3 slot correction groups carry bp_ftq_slot_t
   only, and pft_addr is a block scalar. The entry keeps the p1 view
   for its whole life.

   The two agree on a uBTB HIT, where blk_p1.pft_addr is the uBTB
   entry's fall-through and the uBTB entry mirrors the FTB entry.
   They do NOT agree on a uBTB MISS: the p1 value is the
   block-aligned PC plus FTB_BLOCK_BYTES, the FULL block end, so a
   block terminated by a call earlier in the block pushes an address
   past the call. Allocation is unconditional (5.2), so that entry
   exists and can commit. Nor do they agree after the FE-13 case,
   where the FTB found a branch the uBTB missed and corrected the
   block end while the entry kept the p1 value.

   COST: prediction accuracy on the matching return, not
   correctness. The RAS is a predictor and the return resolves
   against the real target.

   NOT WORKED AROUND. pft_addr is the only candidate the entry
   offers: pc, the slot targets and the slot positions cannot
   reconstruct the value, because nothing records whether the call
   was RVC or RVI, and section 8's "+2 correction for full-width RVI
   calls truncated at a prediction block boundary" needs exactly
   that. THE FIX IS ONE OF TWO PLANNING CHANGES: the p2 group gains
   the FTB fall-through and bp_ftq_entry_t gains a field for it, or
   bp_ftq_entry_t gains a ret_addr field written at p2. Either grows
   ftq_bpu_interfaces.md 4a and ftq_entry_formats.md 2.

W2 R3's GENERATION TEST ON RESOLUTION CANNOT BE BUILT.
   ftq_backend_interfaces.md 7 R3 drops a resolution naming a
   squashed entry "or an entry whose allocation generation does not
   match". ftq_resolve_t.ftq_idx is FTQ_IDX_BITS with no generation,
   and assumption A1 carries FTQ_IDX_BITS + FTB_BR_POS_BITS per
   in-flight instruction and nothing more. So a resolution for a
   squashed entry whose index has been REALLOCATED INSIDE the live
   window is indistinguishable from one for the new use, and only the
   live-window half of R3 is built. Section 9 calls the bit "FE-U7
   work"; FE-U7 resolved without adding one to this path. Closing it
   costs one bit per in-flight instruction and a change to A1.

W3 TD-FE-2, the bp_ftq_meta_t union, remains deferred and ftq_meta is
   built unpacked. When it lands, W2 of ftq_entry_formats.md 3.1 --
   the p3 write SUPPRESSED on the indirect arm -- belongs in
   ftq_meta's write block, and the comment there says so. Nothing
   else in the unit changes.

W4 THE FIVE READ PORTS ON THE FAST PATH ARE A PHYSICAL QUESTION THIS
   PROJECT CANNOT ANSWER. ftq_entry models the array with
   combinational reads, which is a behavioural model and not a
   synthesis directive; banking, port count and registered outputs
   are physical-design choices, and bp_cluster.md's Timing
   Methodology Gap records that this tree has no timing data.

W5 PROPERTY COVERAGE IS SIMULATION-DIRECTED, NOT FORMAL. The 73
   properties are written as concurrent SVA because that is what a
   formal tool consumes (5.7.4), and every one is proven LIVE by
   fault injection -- but live means "fires on the stimulus these
   testbenches produce", not "holds on every input sequence". A
   formal run is the next step and needs no change to these files.

## Other Notes

N1 THE UNIT TESTBENCH DELIBERATELY DOES NOT REPEAT THE LEAF CASES.
   Every acceptance criterion is checked where its stimulus can be
   placed. tb_ftq checks the five things only it can: elaboration,
   the loop, allocation reaching the IFU, the redirect fan-out and
   the commit walk. Restating the leaf cases badly at unit level
   would add coverage numbers and no coverage.

N2 ftq_meta HAS ONE PROPERTY, and that is the honest count. Its
   disjointness rule is a property of the write DATA and is not
   visible on the port list at all, so the testbench proves it by
   writing one group and reading the other back. Binding a property
   that could not fail would be the defect this task is guarding
   against. What IS bindable is that the two read ports are two views
   of one array, which is what a per-port indexing error breaks.

N3 A LINT-ONLY DETAIL WORTH RECORDING. ftq_shadow computes the
   stage-0 view and the accept terms in SEPARATE always_comb blocks.
   Stage 0 is the request ftq_npc is presenting this cycle and the
   accept terms feed ftq_npc's arbitration, so computing both in one
   block makes ftq_npc depend on a block that depends on ftq_npc.
   No signal closes the loop, but the lint reports UNOPTFLAT at
   block granularity. The same shape appeared in ftq_npc, where a
   slot reduction was folded back into itself; both are now separate
   nets.

N4 THE BASELINE WAS BROKEN BEFORE THIS TASK and the tree said
   nothing. Four of the six targets did not build. A task status
   checkbox is not evidence that a task ran, and neither is a green
   report from the session that wrote it -- the packages changed
   underneath BP-106 afterwards. Requirement 0 asks for the tree; the
   tree only tells you what exists, and running it tells you what
   works.

## Where the message budget went

The tooling flagged BASH RESULTS AT ~169k, 17 percent of the window,
with roughly 84.5k of it avoidable. That is the actionable number and
most of it was self-inflicted:

- THE PLANNING DOCUMENTS WERE READ WITH `cat`. `ftq_decisions.md` is
  43KB and `ftq_bpu_interfaces.md` is 37KB. Both exceeded the inline
  limit, were persisted to a tool-results file, and then had to be
  re-read in `sed -n` ranges anyway -- so the first read bought
  nothing and cost twice. Six planning documents, about 5,500 lines
  in total, were the single largest consumer.

- THE FAULT-INJECTION ITERATION was expensive but not wasteful. It
  needed per-case log reads to diagnose why 46 of 73 properties did
  not fire on the first pass, and that diagnosis is what found the
  inert-assertion defect in `ftq_resolve_assert.sv`.

- THE 22-TARGET RUNS WERE CHEAP. Each full sweep was aggregated into
  one line per target inside the shell loop rather than printing
  every build, so a complete clean run cost about 25 lines.

WHAT WOULD HAVE SAVED THE MOST, in order: read large planning
documents with `sed -n` ranges from the start rather than `cat`; grep
for the specific section rather than dumping the file when only one
section is needed; and keep using the aggregate-in-the-loop pattern
for suite runs, which already worked.
